# P-0101 · 给聊天气泡补完整字库：GB2312 1~9 区不能盲烘（撞引擎校验）+ 字形检查器自己会假警

- **工程**：eez-test
- **日期**：2026-10-03
- **工具**：Qoder
- **状态**：fixed
- **标签**：字库,GB2312,eez_font_engine,_glyph_lint,cmap,豆腐块,余量
- **关联提示词**：PR-0136

## 现象（看到什么）

气泡/待机页文本是运行期字符串，原来只烘 CHAT_GLYPHS 演示句 => 真机任意汉字豆腐块；而 _glyph_lint.py 反而把已烘进去的「七择温湿」报成缺字。

## 复现（怎么稳定重现）

把 13px 档种子改成运行时生成的 GB2312 全量后跑 all.py：引擎报 FAIL: Font ... doesn't have any characters included in range 0x3220-0x3220（1~9 区混有 ㈠①℉㎏ 等 CJK 兼容符号，字体没有）。

## 根因（真正的原因）

两处：① 取字集时按 GB2312 区 1~9 盲取，超出该 ttf 实际覆盖；② _glyph_lint 用正则扫 build_ui.py 源码取「已种字形」，看不见运行时算出的常量（3755 字不抄字面串是刻意的），于是假警。

## 修复（做了什么）

汉字只取 16~55 区（3755，实测 cmap 全覆盖）+ 29 个中文标点白名单，且**只烘 13px 一档**；烘前用自写纯 python TTF cmap 解析器全量校验（本机三个 python 都没装 fontTools，别指望能 pip 上）。lint 改成 import build_ui 取模块级字符串常量真值 —— 半路写的产物 cmap 解析器数出 65295 码位明显不对，直接放弃：检查器要么精确要么别上。

## 证据（数字 / 命令输出）

cmap 实测：U+4E00..U+9FFF 覆盖 20909/20992；GB2312 一级 3755/3755、二级 3008/3008、常用标点 0 缺。烘焙后 13px 字形 405->3898、位图 31295->389849 字节（约 +400KB，含描述符）。lint 现报 DSL 可种 3856 码位 / 运行时 155 字 全覆盖。

## 沉淀（新增断言 / 案例 / 文档）

MEMORY.md 加一条：新增运行期文本字号先量余量；检查器必须自证口径

## 追加（2026-10-03 晚，同轮 P-0107 时又踩到本检查器假警，且原因不同）

本条原本记的是「cmap 解析版检查器自己会假警」。这次假警是**另一条路径**：
`_glyph_lint.py` 顶部 `import build_ui`，而 build_ui 需要 Pillow —— 用**系统 python**（无 PIL）
跑时它打印 `!! import build_ui 失败（退回正则扫描）` 然后**继续给结论**：
报「DSL 可种字形 934 个码位 / 运行时 148 字 → 缺字形 4 个：七择温湿」。
换受管 venv 解释器重跑同一份代码 = `3856 个码位 / OK：运行时中文字符全部已种字形`。

⇒ 两个结论：
1. **934 那个数是降级路径扫出来的残缺集**（正则扫不到 build_ui 里的常量），所以"缺字"是假的。
   本条正文早就写过"宁可退回源码扫描也不要没验证过的解析器"，但**退回路径本身也要标注不可信**。
2. 与 all.py 那条同源：**工具链必须用 `C:\Users\Administrator\.workbuddy\binaries\python\envs\default\Scripts\python.exe`**，
   用错解释器不只是跑不动，而是**会给出看起来合理的错误结论**（比裸崩更危险）。
   待办（未获批）：把 `_glyph_lint.py` 的降级分支改成"直接报错退出、不出结论"。

### 再追加（2026-10-03 20:50）：真机报「AI 语气词显示方框」⇒ 新增产物反解工具

用户报聊天里有些字显示成方框。`_glyph_lint.py`（源码侧口径）说"全覆盖"，所以必须换口径：
新增 **`eez-test/design/_glyph_probe.py`** —— 从**已烘好的字体 C 文件**反解真实码位集。

★ 第一次反解就踩到 LVGL cmap 的读法陷阱：`LV_FONT_FMT_TXT_CMAP_SPARSE_TINY` 段的
`unicode_list_N[]` 存的是**相对 `range_start` 的偏移**，不是绝对码位。当绝对值读会得到
荒谬结论（我报成"中文标点 26 个全缺"，而截图里逗号句号明明正常）。正确式子：
`码位 = range_start + 偏移`；只有 `FORMAT0_TINY` 段才是 `[range_start, +range_length)` 连续。
修好后 13px 反解 = 4 段 / **3897 码位**（与 96+3184+17+600 对得上，也与 P-0101 正文的 3898 字形一致）。

实测缺口（这就是用户看到的方框）：
- **语气词缺 7**：呃 U+5443 / 呗 U+5457 / 喔 U+5594 / 喽 U+55BD / 嘞 U+561E / 噢 U+5662 / 欸 U+6B38
- **口语常用字缺 4**：咦 U+54A6 / 咩 U+54A9 / 哒 U+54D2 / **嗯 U+55EF**
- 中文标点只缺 ￥ U+FFE5（说明"方框"不是标点问题）
- **符号与 emoji 全缺**：℃ ± × ÷ ★ ○ ● ✓✗ 以及 😀🎵❤✨🌞 —— 13px 只烘了 GB2312 一级 + 标点白名单
⇒ 根因口径要说清：**烘的是"静态可枚举集"，而云端回复是自由文本** —— 只要 AI 用了一个
不在 GB2312 一级的口语字（嗯/噢/嘞…）或一个 emoji，就必然是方框。这不是截断逻辑的 bug。

三条待批路线（按体积算过，app 分区 8MB 现用 4.38MB = 52.2%，余 3.82MB）：
1. 补 GB2312 **二级** 3008 字 + 上面 11 个口语字 ⇒ 约 +300KB（cmap 实测二级 3008/3008 在 TTF 里都有）；
2. 烘**全 CJK** U+4E00..U+9FFF 20992 字 ⇒ 约 +2.0MB，装得下（会到 ~76%），一次性消灭中文方框；
3. emoji 烘不了彩色 ⇒ 只能在 native 侧**过滤**（`chat_copy_clip` 剔除无字形码位）或替换成文字标记。

# P-0118 · 歌词块是设计稿假词：接同名 .lrc，当前行恒居中（样式静态时靠窗口对齐做高亮）

- **工程**：p4_touch_lcd4_3_exp/lvgl_demo_ai/eez-test
- **日期**：2026-10-07
- **工具**：Qoder
- **状态**：fixed
- **标签**：歌词,LRC,UTF-8,字库档位,EEZ静态样式,PSRAM,P4零阻塞,单写者
- **关联提示词**：PR-0186

## 现象（看到什么）

正在播放页那 5 行「歌词」是设计稿字面量（build_ui.py 里写死 飞机飞过天空 / 我在黑夜中醒来 …，没绑任何变量）⇒ 真机放哪首都显示同样几句，是假反馈。用户点单：歌词要同步，并且明确「不参考设计稿这部分」（这块不必再和 G5 稿对齐）。

## 复现（怎么稳定重现）

真机：随便放一首，屏上永远是那 5 行假词。PC：design/sim.py 走路脚本 lyric —— 基线 gettext m_np_lyr2 → 点滑杆跳到 74% → 再读 m_np_lyr1/2/3 → 暂停后再读。另一条分支：EEZ_SIM_LRC=none 跑同一支。

## 根因（真正的原因）

不是渲染问题，是**根本没有歌词数据源**：DSL 里那 5 个 label 既没 var 也没 id，文本是常量；native 侧也没有任何 LRC 解析。顺带查清两个约束：①13px 档已烘 GB2312 一二级全量（~6770 字），16px 档只烘了演示曲名 + 两枚头像图标 ⇒ 歌词这种任意中文只能走 13px，否则必出豆腐；②EEZ 的 label 字号/颜色是静态样式，运行期改不了 ⇒「当前行高亮」不能靠改样式实现。

## 修复（做了什么）

新增 src/native/platform/io_lyrics.{h,cpp}（两端共用，读文件那半截用 ESP_PLATFORM 隔开）：
1) 数据源 = **与音频同名的 .lrc**（/sdcard/music/这条街.mp3 → 这条街.lrc）。不联网、不动曲表结构（曲表里不存歌词路径，播放时由音频路径换后缀即得，零额外静态）。
2) 解析支持：mm:ss / mm:ss.xx / mm:ss.xxx / mm:ss:xx；**一行多个时间标签共用同一句**；[offset:±…] 全局偏移；[ti:][ar:][by:] 等字母标签忽略；CRLF 行尾；UTF-8 BOM；解析后插入排序兜乱序。**逐句 UTF-8 校验**，非法句丢掉并计数（国内下的 LRC 一半是 GBK，当 UTF-8 用就是满屏豆腐，比不显示更坏）；整首都不是 UTF-8 时给一条明确日志让用户转码，不做 GBK→UTF-8 转换（要带转换表，不值当）。
3) 分工守 P4 铁律：**读文件 + 解析在播放任务里**（io_music_player 开曲成功后调 lyr_load_for_audio），LVGL 线程一次都不碰 SD；发布在 LVGL 线程每拍调 lyr_publish(sec)，**行号没变直接 return**，不产生任何变量写。表无锁：写者唯一，且 s_n 是最后一步才提交的单字对齐写（RV32 原子），读侧永远只看到已提交行数以内。
4) 显示模型：5 格固定窗口，**当前行恒在中间格（slot 2）**，中间格白、其余灰 —— 高亮靠窗口滑动实现，所以只需要两种静态样式，绕开 EEZ 不能运行期改样式的限制。字号统一 13px（理由见根因）。想要「当前行更大」的对比，得给 16px 也补全量字库（约 +700~900KB rodata，app 分区还剩 3.2MB），本轮没做。
5) 边界：有词但还没唱第一句 ⇒ 窗口停在第一句，不显示「暂无歌词」；只有真没歌词文件才显示。换卡/曲表被换空 ⇒ io_music_rescan 里 lyr_reset()（旧表是另一首歌的）。
6) 配套：APP_IN_LYR_0..4 五个字符串输入 + native_vars 里宏生成 5 对 get/set（set 空实现）；把 APP_IN_STR_MAX 从 app_model.cpp 挪进 app_model.h —— 发布方要按它准备缓冲区并**自己截在 UTF-8 字符边界**（app_set_input_s 是按字节 strncpy，交给它截会切出半个字）；表放 PSRAM（EXT_RAM_BSS_ATTR，300 句 ×96B ≈ 29KB）；CMakeLists 的 NATIVE_SRCS 加新文件。

## 沉淀（新增断言 / 案例 / 文档）

1) 「高亮当前行」在**样式静态**的生成式 UI 里，正确解法不是改样式，而是**把窗口对齐到当前行**：当前行永远落在中间格，高亮就退化成一个固定样式，零运行期样式操作。
2) 运行期文本要先查**字库档位**再定字号：本工程 13px 有 GB2312 一二级全量、16px 只有曲名，选错档位就是豆腐块；而这类缺字 _glyph_lint 查不出来（它只扫 DSL 静态字）。
3) 跨线程共享一张表又不想加锁，就把不变量做出来：**写者唯一 + 行数最后提交**，读侧以提交计数为界。比塞一把 portMAX_DELAY 的锁更守 P4 零阻塞铁律。
4) 慢操作（读 SD 上的 .lrc）放进已经在跑 SD 的那个任务，而不是给 UI 线程加一次同步 IO；发布端「值没变就不写」是省掉每拍 5 次 label 更新的关键。
5) 中文文本上屏前先验 UTF-8：GBK 的 LRC 很常见，宁可显示「暂无歌词」+ 一条说清编码的日志，也不要屏上乱码 —— 乱码会让人以为功能坏了。
6) ★ 本轮同时踩到一个待办冲突：P-0117/P-0115 那串「PSRAM 堆被踩」还没定位，而歌词模块又往 PSRAM 加了 ~29KB 静态 + 每首歌一次 SD 读。**差分取证要在这一版上做**，别拿旧固件的结论套新固件（内存布局变了，崩点会挪）。

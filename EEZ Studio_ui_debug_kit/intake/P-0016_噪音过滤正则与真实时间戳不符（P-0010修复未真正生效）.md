# P-0016 · Chromium 噪音过滤正则与实际时间戳格式不符（P-0010 的修复并未真正生效，假阳性复发）

- **工程**：test.eez-project（EEZ Studio CLI build）
- **日期**：2026-09-24
- **工具**：WorkBuddy
- **状态**：fixed
- **标签**：eez,ci,regex,false-positive,复发
- **关联提示词**：PR-0031（"继续"）

## 现象（看到什么）

`design/eez_build.py` 报：

```
Build successfully finished at 2026/9/24 07:03:15
!! 构建报错 9 条
```

即**构建明明成功**，脚本却 return 1。
P-0010（2026-09-23）曾记录并"fix"过同一问题，说明**当时那次修复并没有真正生效**。

## 复现（怎么稳定重现）

```bash
python design/eez_build.py ; echo $?
# 观察 design/_eez_build.log 里 Chromium 噪音行的真实写法
grep -i error design/_eez_build.log | head
```

噪音行原文：

```
[33828:0924/070307.618:ERROR:net\disk_cache\cache_util_win.cc:25] Unable to move the cache: 拒绝访问。 (0x5)
```

## 根因（真正的原因）

**时分秒是连写的 `070307.618`，没有冒号分隔**；
而当初实现的过滤正则写成了：

```python
r"^\[\d+:\d{4}/\d+:\d+:\d+\.\d+:(ERROR|WARNING|INFO):"     # 要求 07:03:07.618
```

`\d+:\d+:\d+\.\d+` 期待三节以冒号分隔的时间，实际日志只有一节 —— **永远匹配不上**，
于是 9 条 disk_cache / GPU 缓存警告被当成构建错误。

**为什么当时没发现**：P-0010 记录的"证据"是"过滤前 9 条、过滤后 0 条"，
看起来生效了，但实际上那次是**噪音行恰好没出现**（Chromium 缓存创建偶发失败），
属于**间歇性静默** —— 换个时机跑就复发。

## 修复（做了什么）

`design/eez_build.py`：把时间那段改成兼容"连写"与"带冒号"两种写法：

```python
CHROME_NOISE = re.compile(r"^\[\d+:\d{4}/\d+(?::\d+)*\.\d+:(ERROR|WARNING|INFO):")
#                                          ^^^^^^^^^ 关键：(?::\d+)* 允许省略冒号节
```

同时把注释写清"旧正则为什么匹配不上"，避免后人再改回去。

## 证据（数字 / 命令输出）

```
# 修复前
python design/eez_build.py | tail -1   →  !! 构建报错 9 条（exit 1，但产物完整）
# 用修复后的正则直接打同一份日志：噪音 9 条全部被识别为 CHROME_NOISE

# 修复后
python design/eez_build.py             →  构建完成     exit 0
```

- **`skills.md` §11.3.1 的正则原本就是错的**（把这条 bug 文档化了），已按修正后的写法规正，
  并补上"日志时间戳连写、不要用冒号分节去写正则"的说明。
- **`intake/P-0010`** 追加"补充"段指向本篇（按"只追加不改历史"的约定，未改原文）。
- **教训（比正则本身更值钱）**：
  1. **"间歇性"的 bug，证据必须来自"复现那一次"，不能来自"恰好没报错的那一次"。**
     P-0010 当时用"过滤后 0 条"当作修好，其实只是那一轮没触发。
  2. 判定"构建是否真失败"要**以权威标记为准**（如 `Build successfully finished`），
     噪音过滤只用于**降噪**，不应反向决定结论。
  3. 写日志过滤正则前，**先 `grep` 一行真实日志贴进来**，不要凭印象猜格式。

> **本文件是 `ui_debug_kit` 工具箱的核心方法论**，同目录还有：
> `README.md`（快速上手）· `skills.md`（操作手册：自动设计 / 对照查验 / 仿真验证）·
> `INTAKE.md`（★ 记录规约：新问题 / 提示词怎么留痕）·
> `config.template.json`（配置模板）· `CONFIG.md`（字段与迁移清单）·
> `tools/`（可直接执行的工具）· `cases/`（案例库）·

> 本手册**跨项目、跨框架通用**：正文不含任何具体工程的路径、字体名、屏名或数值。
> 你的工程差异只写在**工程侧的 `ui_debug_kit.config.json`** 里，本手册不需要改。
>
> **第一原则：先出图 → 再对照 → 才改代码。任何"看起来对"的判断都必须有像素级或数值证据。**

## 0. 怎么用本手册（AI 执行约定）

1. **先确认配置存在**：`python tools/kit.py`。缺配置时按 `CONFIG.md` 从 `config.template.json` 建一份，
   **建在工程里**（工具会自动向上查找），不要把工程信息写进工具箱目录。
2. 要出图 → 查 §3 选对应栈的手法。
3. 要查错 → §2.4 的"差异量化四步法" + §2.5 的"标定法"，再对照 §4 的坑清单。
4. 要跑体检 → §2.6 的六类检查 + §6 的代码模板 / `tools/` 里的现成脚本。
5. 改完代码 → 必须走 §2.3 的回归闭环，给数值证据。
6. 解决了一个非平凡问题 → 按 `cases/README.md` 的模板追加一个案例。
7. **留痕（必做）** → 按 `INTAKE.md`：每轮把用户提示词追加进 `prompts/PROMPT_LOG.md`，
   遇到新问题登记进 `intake/`。`tools/log_entry.py` 是通用写入器，任何 AI 工具都能调。

术语约定：

| 术语 | 含义 |
|---|---|
| **设计源** | 描述界面的唯一权威文件（DSL / 设计稿 JSON / 原始工程文件） |
| **效果图 / 预览图** | 由设计源渲染出的示意图（供人评审外观） |
| **原生渲染图** | 由**目标渲染引擎本身**画出的像素图（最可信的验收依据） |
| **交叉验证图** | 由"编译/转换后的产物"再渲染出的图，用于验证转换链路无损 |
| **墨迹（ink）** | 实际被点亮的像素集合；字形墨迹 ≠ 控件框 |
| **组件框（box）** | 布局系统里声明的坐标与尺寸 |

## 1. 项目配置（**不要把这些信息写进工具箱**）

配置字段的完整说明见 `CONFIG.md`；模板见 `config.template.json`。
下面只列"必须实测、不能猜"的几项。

### 1.1 变量占位符（手册与代码模板里统一使用）

| 占位符 | 含义 |
|---|---|
| `{ROOT}` | 工程根目录 |
| `{DESIGN_DIR}` | 设计源与工具目录 |
| `{DESIGN_SRC}` | 设计源文件 |
| `{PROJECT_FILE}` | 目标工程/产物文件 |
| `{GEN_DIR}` | 生成的代码目录 |
| `{EXE}` | 目标 IDE / 运行时可执行文件 |
| `{PY}` / `{PYV}` | 运行工具的解释器（`{PYV}` 指已装绘图/字体库的那个） |
| `{NODE}` | Node 解释器 |
| `{SCREEN_W}` / `{SCREEN_H}` | 屏幕或画布尺寸 |
| `{DEVICE_FONT}` | 设备实际使用的正文字体文件 |
| `{ICON_FONT}` | 图标字体文件 |

### 1.2 坐标与度量（**最容易搞错，必须实测**）

| 项 | 为什么要实测 | 怎么测 |
|---|---|---|
| 坐标系语义 | 设计源常用绝对坐标，运行时子元素多为相对父元素；不换算会层层偏移 | 对比设计源坐标与产物坐标 |
| 屏幕原点 | 左上 / 左下 | 看画布约定 |
| 字号档位 | 设计稿常写"不存在的中间字号"，会被回退到最近档 | 在目标工程里列出真实存在的字号 |
| 字体度量 | **必须读实际生成物**，配置面板的值经常不等于生效值 | 读生成的字体数据（`line_height`/`base_line`）→ 换算 ascent |
| 墨迹偏移 | 字形墨迹相对控件框顶的偏移，是判断"裁没裁"的基准 | `tools/ink_check.py --against` |
| 默认主题偏移 | 某些控件类型会给子元素加默认内边距，使"声明坐标 ≠ 渲染坐标" | 同类控件分别放进容器与目标控件，各测一次 |
| 墨迹阈值 | 太低会把底色算成内容 | `tools/ink_check.py --rows` 看底色亮度 |
| 边界是否有分隔线 | 画布最外一行/列常是纯色分隔线，会误报"触底" | 看该行像素是否整行同色 |

### 1.3 采集清单（开新工程时逐项确认）

```
[ ] 设计源是什么文件？谁生成它？（单一设计源是否成立，见 §2.2）
[ ] 目标工程文件是什么格式？（JSON / 数据库 / 二进制 / 目录）
[ ] 生成物有哪些？路径在哪？（代码、资源、字体、图片）
[ ] 运行时能不能在本机跑起来？渲染器是什么？（Chromium? 自绘? 平台方?）
[ ] 出图手段候选：① 目标引擎自有截图 API ② CDP ③ 离屏渲染 ④ 自写软件渲染器
[ ] 屏幕分辨率与色彩/不透明度语义（是否有 alpha、是否 premultiplied）
[ ] 字体：设备实际字体文件、字号档位、图标字体来源、字形白名单机制
[ ] 主题默认样式：对容器/按钮/文本分别有什么默认值？
[ ] 工程保存时会不会重算布局？（有的 IDE 会用自己算的字宽覆盖坐标）
[ ] 构建流程会不会清理某些生成物？顺序是什么？
```

### 1.4 环境雷区（各项目都会遇到）

- **PATH 偶发丢失**：某些 shell 环境下 `ls`/`cd` 会突然 not found。每条命令前先
  `export PATH="/usr/bin:/bin:/usr/local/bin:$PATH"`（Windows 追加 `/c/Windows/System32:/c/Windows`）。
- **路径风格**：把 `C:/...` 或 `/c/...` 传给原生程序（Python/Node）时可能被当字面量。
  **先 `cd` 进目录，再用相对路径**，最稳。
- **子进程环境变量污染**：某些 Electron 应用在 `ELECTRON_RUN_AS_NODE=1` 下会退化成纯 Node。
  启动前显式 `env -u ELECTRON_RUN_AS_NODE`。
- **长命令超时**：构建类命令可能"报超时但实际已完成"——**以产物 mtime/内容为准**，不要盲目重跑。
- **编码**：脚本统一 `# -*- coding: utf-8 -*-`，读写文件显式 `encoding="utf-8"`。

## 2. 通用方法论

### 2.1 三层图策略（**核心：一张图证明一件事**）

不要只出一种图。三种图各有职责，混用会导致误判：

| 层 | 数据来源 | 能证明 | 不能证明 | 什么时候用 |
|---|---|---|---|---|
| **① 设计预览图** | 设计源 | 外观设计、布局意图 | 转换/编译是否无损；目标引擎真实渲染 | 设计迭代、快速评审 |
| **② 交叉验证图** | **编译/转换后的产物** | 转换链路无损（坐标/样式/字体引用没被改） | 目标引擎真实渲染 | 每次改完设计源后必跑 |
| **③ 原生渲染图** | **目标渲染引擎**（真机/模拟器/运行时画布） | **最终事实**：设备上就是这个样子 | —（注意 §2.7 的度量差异） | 验收、疑难问题定案 |

**判读规则**：
- ① 与 ② 逐像素一致 → 转换链路可信，可继续。
- ② 与 ③ 有差异 → "引擎实际渲染 ≠ 数据描述"，去查默认主题、字体度量、渲染语义（§4）。
- 只有 ③ 才能用来向用户展示"最终效果"。

### 2.2 单一设计源原则（**违反必然出"两张皮"**）

```
        ┌─→ 渲染器A → 效果图
设计源 ─┼─→ 转换器  → 目标工程 → 目标引擎 → 原生渲染图
        └─→ 渲染器B → 交叉验证图
```

- **绝不为"效果图"和"产品代码"各写一套实现**：两套实现必然漂移，漂移后谁对谁错说不清。
- 渲染器 A/B 应**实现同一套渲染语义**（相对坐标累加、圆角、alpha 混合、逐字符字体选择、文本基线），
  差异只允许出现在**光栅化细节**（抗锯齿算法、hinting）。
- 若无法与目标引擎语义完全对齐，就明确记录"哪些差异是允许的"。

### 2.3 对照修复闭环（五步）

```
① 复现并出图  →  ② 量化差异（数值，不靠肉眼）  →  ③ 定位到具体控件/数据
      ↑                                                        ↓
⑤ 回归验证（全量 + 逐像素）  ←  ④ 改设计源**一处** + 重跑转换
```

纪律：
- 改动只落在**设计源**（及必要的工具脚本），不手改转换产物。
- 每次转换自动备份产物（`<file>.bak-<时间戳>`），保证可回滚。
- 每轮结束必须给出**数值证据**：像素计数、墨迹包围盒、坐标比对、断言通过数。

### 2.4 差异量化四步法（对照的核心手法）

**不要用眼睛找差异。** 按下面四步收敛：

#### 第 1 步 · 量化：结构性差异还是光栅差异？

```python
from PIL import Image, ImageChops
a = Image.open("ref.png").convert("L")      # 期望图
b = Image.open("actual.png").convert("L")   # 实际图（尺寸必须先对齐）
dif = ImageChops.difference(a, b)
hist = dif.histogram(); total = a.width * a.height
big = sum(hist[64:])      # 亮度差 ≥64 → 结构性（缺元素 / 错位 / 缺字 / 被裁）
mid = sum(hist[24:64])    # 中等 → 可能整体移位
print("大差异 %d (%.4f%%)  中等 %d" % (big, 100.0 * big / total, mid))
```
判读：`big == 0` → 一致；`big/total < 0.05%` 且形状一致 → 抗锯齿/取整，可忽略；其余 → 继续。

#### 第 2 步 · 聚类：差异集中在哪？

```python
pts = [(x, y) for y in range(H) for x in range(W) if dif.getpixel((x, y)) >= 64]
from collections import Counter
for (gx, gy), cnt in Counter(((x // 40 * 40, y // 40 * 40) for x, y in pts)).most_common(10):
    print("区域 x=%d..%d y=%d..%d : %d px" % (gx, gx + 40, gy, gy + 40, cnt))
```
差异形状能直接指认元素：**细长竖条 = 字形**；**方块 = 图标/图片**；**整行 = 基线**；
**边缘一圈 = 圆角/描边**；**成片矩形 = 背景或内边距**。

#### 第 3 步 · 测量：**量墨迹，不量框**

控件框（box）是布局声明，墨迹（ink）才是实际像素。两者经常不等 —— 尤其当父容器有默认
padding、或字体有上下留白时。

```python
def ink_bbox(img, x0, y0, x1, y1, thr=140):
    pts = [(x, y) for y in range(y0, y1) for x in range(x0, x1) if img.getpixel((x, y)) > thr]
    if not pts: return None
    return (min(p[0] for p in pts), min(p[1] for p in pts),
            max(p[0] for p in pts), max(p[1] for p in pts))
```
把墨迹包围盒与"沿父链累加得到的绝对坐标"比对 → 得到**偏移量 (dx, dy)**。

#### 第 4 步 · 判定表

| 差异形态 | 含义 | 排查方向 |
|---|---|---|
| 形状一致、整体平移 (dx,dy) | 坐标系/内边距问题 | 父链绝对坐标；父容器/控件是否有**默认 padding、border、min-size、layout**（§4.1/§4.2） |
| 平移只发生在某类控件内 | 该控件类型的默认样式 | 逐控件类型对照：容器 vs 按钮 vs 列表项 |
| 文字缺笔画 / 方框 / 空白 | 字形没进字体 | 字符集白名单、附加字体源、字号档位（§4.4） |
| 文本折成两行 | 框宽 < 文本真实宽度 | 用**真实字号**量宽度；别用固定宽 + 对齐属性（§4.5） |
| 元素被边界切开 | 越界 | 墨迹包围盒 vs 画布边界（**最外一行常是分隔线，见 §2.5**） |
| 整块元素消失 | 未编译进产物 / 被父层遮挡 / alpha=0 | 比对产物里的节点数；查父层背景不透明度 |
| 差异随页面切换而变 | 异步渲染未完成 | 抓图前等"画面真正变化"（§4.6） |

### 2.5 基准标定法（判断"到底裁没裁"的关键技巧）

**问题**：一个贴着边界的元素，怎么判断它是"没被裁"还是"被裁了但看不出"？
**方法**：找一个**同类、同字号、且远离边界**的元素做基准，量出它的墨迹相对自身框的偏移，
再把偏移套到可疑元素上，反推真实墨迹范围。

```
基准：某个 20px 文本，框顶 = 40，实测墨迹 41..60   →  偏移 +1..+20
套用：另一个 20px 文本，框顶 = T   →  墨迹必然 = T+1 .. T+20
      要求 T+20 ≤ 画布下边界，否则就会被裁
```

**两个必须注意的细节**：
1. **水平方向比垂直方向干净**：垂直方向受基线影响会有多解；水平方向的偏移是唯一的。
   判断"控件框与渲染位置是否一致"时，**优先用水平墨迹**。
2. **边界那一行可能是分隔线而非内容**：统计"是否触底"时要先看该行是否整行同色：
   ```python
   row = [img.getpixel((x, H - 1)) for x in range(W)]
   uniform = len(set(row)) <= 2          # 整行近似同色 → 是分隔线/底色，不是内容
   ```

### 2.6 自动体检清单（可套用到任何 UI 工程）

每轮改完都跑，**六类**：

| # | 检查 | 判据 | 失败含义 |
|---|---|---|---|
| 1 | **几何/越界** | 遍历组件树，所有元素（尤其**墨迹**）落在画布内；文本宽 ≤ 框宽 | 会被裁 / 换行 |
| 2 | **资源覆盖** | UI 引用到的每个字符/图标/图片/字体名，都在产物里存在 | 缺字、空白、回退字体 |
| 3 | **导航/引用完整性** | 所有跳转/链接/资源引用目标都存在（0 死链）；入口页正确 | 点了没反应 / 死链 |
| 4 | **产物一致性** | 生成代码里的符号 引用 ↔ 声明 ↔ 定义 三方 1:1；无非法值（负坐标等） | 编译不过 / 运行异常 |
| 5 | **运行时接线** | 入口初始化被调用；事件/动画/消息泵被**周期驱动**；没有错误的头文件包含 | **交互无响应**（最典型） |
| 6 | **回归对照** | ② 与 ① 逐像素差异为 0；③ 与 ② 无结构性差异 | 转换或渲染语义有偏差 |

> 第 5 项最容易被忽略，却最常导致"点了没反应"：**动作只是入队，没人驱动队列就永远不会执行**。
> 检查点：主循环里是否有周期性 tick/flush 调用；事件监听是否真的注册。

### 2.7 判定优先级（数据源可信度排序）

出现"面板说没问题、实际有问题"时，按此优先级取信：

```
① 目标引擎的实际渲染像素        （最终事实）
② 生成物的实际参数（读文件）     （如字体数据里的 line_height / base_line、生成代码里的坐标）
③ 工程/IDE 里的配置面板数值      （**只是配置意图，不保证等于运行结果**）
```

**切记**：配置值 ≠ 生效值。**所有布局计算读 ②，不要读 ③。**

## 3. 拿"原生渲染图"的通用手法

### 3.1 为什么优先"从运行中的渲染器里 dump 像素"

- **优于 OS 截屏**：无头/无桌面环境没有可见窗口；截屏还会带上窗口边框、缩放、系统 DPI。
- **优于自己模拟**：自写渲染器只能证明"我以为的样子"，无法证明引擎的真实行为。
- **能拿到就优先拿**：目标引擎的 framebuffer / canvas / 离屏表面。

### 3.2 Chromium 系（Electron / CEF / 浏览器 / PWA）—— 通过 CDP

适用于所有 Electron/Chromium 宿主（含各种 IDE、设计工具、Web 应用）。
配套脚本：`tools/cdp/launch.sh`（启动）+ `tools/cdp/grab.js`（抓图）。

**① 带调试端口启动**

```bash
env -u ELECTRON_RUN_AS_NODE "{EXE}" \
  --remote-debugging-port=9222 \
  --no-sandbox --disable-gpu --enable-unsafe-swiftshader \
  --disable-dev-shm-usage --disable-features=CalculateNativeWinOcclusion \
  "{PROJECT_FILE}" &
# 等端口就绪
for i in $(seq 1 15); do curl -s --max-time 1 http://127.0.0.1:9222/json/version >/dev/null 2>&1 && break; sleep 1; done
```

参数避坑表（无 GPU 环境通用）：

| 参数 | 结论 |
|---|---|
| `--remote-debugging-port=N` | 打开 CDP，**必需** |
| `--enable-unsafe-swiftshader` | 无 GPU 时靠软件渲染兜底，**必需** |
| `--disable-software-rasterizer` | **绝不能加**（关掉兜底，必崩） |
| `--in-process-gpu` | **绝不能加**（GPU 初始化失败会拖死主进程） |
| `--no-sandbox` | 容器/受限环境常需要 |
| `ELECTRON_RUN_AS_NODE` | **必须清掉**，否则 Electron 退化为纯 Node |
| `--disable-dev-shm-usage` | 共享内存小的环境需要 |

**② 连 CDP，三种取值方式**

```bash
curl -s http://127.0.0.1:9222/json/list      # → 每个 target 的 webSocketDebuggerUrl
```

连上 WebSocket 后发 JSON-RPC：

```js
const send = (method, params = {}) => new Promise(r => {
  const i = ++id; pend.set(i, r);
  ws.send(JSON.stringify({ id: i, method, params }));
});

// A. 取画布像素（最精确：无窗口装饰，尺寸=画布尺寸）
const r = await send("Runtime.evaluate", {
  expression: `JSON.stringify([...document.querySelectorAll('canvas')]
      .map((c,i)=>({i,w:c.width,h:c.height,d:c.toDataURL('image/png')})))`,
  returnByValue: true });

// B. 取整窗（走 compositor，**无需可见窗口**）
const s = await send("Page.captureScreenshot", { format: "png" });

// C. 读界面文本（排障神器：抓错误提示原文）
const t = await send("Runtime.evaluate", {
  expression: `document.body.innerText.slice(0,4000)`, returnByValue: true });
```

**WebGL 场景**：`toDataURL()` 可能返回空白（帧缓冲已被清除）。对策：在 `requestAnimationFrame`
回调里取；或让应用开启 `preserveDrawingBuffer`；兜底用 `Page.captureScreenshot` + `clip` 裁剪到画布区域。

**③ 三个必踩的坑**

| 坑 | 现象 | 解法 |
|---|---|---|
| 画布未挂载 | `querySelectorAll('canvas')` 返回 0 | 画布常常**只在打开了对应视图/标签时才挂载** → 用合成事件点开它：`['mousedown','mouseup','click','dblclick']`，且 `{bubbles:true, view:window}`（React/Vue 靠事件委托） |
| 拿到上一帧 | 多张图 md5 相同 | **只有像素与上一帧不同才落盘**；过滤过小的空白图（单色图压缩后极小） |
| 进程自行退出 | 抓几秒后进程消失 | 启动后立刻轮询就绪即抓；一次会话只抓少量目标，必要时**重启抓下一个** |

### 3.3 其他栈怎么拿原生图（速查）

| 栈 | 推荐手法 | 要点 |
|---|---|---|
| 嵌入式 | ① 厂商 IDE 的预览/模拟器 ② PC 模拟器 dump framebuffer ③ 真机截屏接口 | 优先"编辑器内预览"（通常就是引擎本尊渲染），其次 PC 模拟器 |
| Qt Widgets / QML | `QWidget::grab()` / `QQuickWindow::grabWindow()` / `Item::grabToImage()` | 支持无头：`QT_QPA_PLATFORM=offscreen` |
| Flutter | golden test / `RepaintBoundary.toImage()` | golden 天然就是"逐像素对照" |
| Android | Compose/Screenshot 测试、`PixelCopy`、`adb exec-out screencap` | 模拟器可无头 |
| Web / PWA | Playwright/Puppeteer 截图 或 `element.screenshot()` | 可 `deviceScaleFactor` 超采样 |
| 自绘引擎 | 写 software renderer（PIL/Skia/canvas）复刻绘制语义 | 必须声明"哪些差异是允许的"（§2.2） |

## 4. 组件树类 UI 的通用坑（与框架无关的心智模型）

> 以下 8 条**跨框架反复出现**，只是各栈表现形式不同。遇到相似现象先来这里对号入座。
> 每条都配有真实案例，见 `cases/`。

### 4.1 相对坐标 vs 绝对坐标

- **现象**：嵌套容器里的子元素跑到屏幕外，或位置"多叠了一层"。
- **真因**：设计稿常用绝对坐标书写，而运行时子元素坐标是**相对父元素**。嵌套几层就偏几层。
- **通用解法**：在"设计源 → 产物"的转换步骤里做统一换算（沿树累减父坐标），并加自检：
  产物里的坐标应**全部非负且不超过父容器**。
- **各栈表现**：多数组件树框架子元素都相对父；SVG 与部分设计工具是绝对；
  Web `position:absolute` 相对最近的定位祖先。

### 4.2 默认主题样式覆盖手写坐标（**最隐蔽**）

- **现象**：控件里手写的坐标全都"差一点点"，且**只发生在某类控件**里（同尺寸的其他控件没事）。
- **真因**：框架默认主题/样式给这类控件加了 **padding / border / min-size / 默认布局**，
  子元素被整体推开。
- **判别方法（关键技巧）**：
  1. **同类控件横向对比**：容器里的元素正常、按钮里的元素偏移 → 问题在按钮的默认样式。
  2. **用水平墨迹量偏移**（水平无基线歧义）：`实际墨迹左边界 − 声明左边界 = padding_left`。
  3. **看两个方向的偏移是否不等**：两方向不同值 → 几乎确定是控件自带 padding；
     坐标换算错误会让两个方向**同比例**偏移。
- **通用解法**：在样式里**显式清零**（`padding: 0` / `border: 0` / 关闭布局），
  让"声明坐标 == 渲染坐标"；此后所有坐标计算才有意义。
  不要"反向补偿"那个偏移 —— 补偿是打补丁，清零才是根治。
- **各栈表现**：HTML `<button>` 有 UA 默认样式；Android 主题有 `?attr/buttonStyle`；
  Flutter `Button` 自带 `padding` + `minimumSize`；组件树框架的默认主题同样会给按钮加内边距。

### 4.3 文本度量：配置值 ≠ 生效值

- **现象**：按面板上写的字号/行高布局，结果文字画高了/画低了 N 个像素。
- **真因**：面板里的 `ascent/descent/line-height` 是**配置意图**；真正生效的是**生成物里**的值。
  两者经常不一致（差 2px 就足以让贴底文字出界）。
- **通用解法**：布局计算**读生成物**（§2.7 优先级 ②）。做一个"度量提取"步骤，
  把生效值缓存成常量，供渲染器与校验脚本共用。
- **自检**：写一个断言，比较"面板配置值"与"生成物实际值"，不一致就打印告警。

### 4.4 图标/特殊符号字体必须与文本字体分离

- **现象**：图标全是空白/方框；或中文全变方框而英文正常。
- **真因**：图标字体（图标字体 / IconFont / emoji 等）与正文字体是**不同文件**；用错字体取字形必然失败。
  更隐蔽的是：**把图标码位混进正文字体的字符集白名单**，会让工具尝试从正文字体提取图标 →
  **整份字体提取失败**（于是正文也一起坏掉）。
- **通用解法**：
  1. 正文字体只声明**正文 + 语言字符集**；
  2. 图标码位声明在**独立的附加字体源**（指向图标字体文件）；
  3. 渲染/测量时**逐字符选择字体**：落在图标私有区（如 U+E000–U+F8FF）→ 图标字体，否则正文字体；
  4. 加断言：UI 用到的每个码位都必须能在**某个已声明源**里找到。
- **各栈表现**：Web 用 `font-family` 回退链 + `@font-face unicode-range`；
  Android 用 `fontFamily` + `ttc`；组件树框架各有自己的"字符集白名单 + 附加源"机制。

### 4.5 居中/对齐：用算出来的坐标，别用对齐属性

- **现象**：设计源里居中正常，但产物里位置跑偏（甚至变成负坐标）。
- **真因**：某些 IDE **在保存/序列化时会按自己算的字宽重新居中**，覆盖你的意图；两边字宽算法不同 → 偏。
- **通用解法**：**放弃"固定宽 + 对齐属性"**，改用 `content 宽度 + 按真实文本净宽算出的坐标`。
  宽度随内容、位置自己算 —— 序列化工具没有可重算的余地。
- **注意**：算居中用**净宽**（不带防换行余量）；算右对齐/换行判定用**含余量**的宽度。

### 4.6 异步渲染：抓图必须等"画面真的变了"

- **现象**：连续抓多张图，内容重复（md5 相同）。
- **真因**：渲染是异步的；上一帧的表面仍然存在，"发现元素就取"会取到旧帧。
- **通用解法**：**轮询直到像素/内容与上一帧不同**才落盘；设置超时与"未变化"上报。
  必要时先触发一次重绘（切页、滚动、resize）。

### 4.7 构建会清理某些生成物（顺序敏感）

- **现象**：跑完构建后，某些生成物（字体/图片/资源）**消失**或**没被重新生成**。
- **真因**：IDE/构建系统把"由 GUI 交互触发的生成步骤"和"CLI 构建"分开了；CLI 只清理不重建。
- **通用解法**：
  1. 把这类生成物改为**离线脚本产出**（不依赖 GUI 交互），纳入可重复流水线；
  2. 固化执行顺序（先构建 → 后生成资源），并在脚本/文档里注明"顺序不能反"；
  3. 加产物存在性断言，缺失就 fail 而不是静默通过。

### 4.8 边界与"最后一像素"

- **现象**：内容贴着画布边缘、看起来"被切了一点点"。
- **通用解法**：
  - 一律用**墨迹**（不是框）判断越界；
  - 预留 **≥2px** 安全边距（不同引擎的基线/取整规则不同）；
  - 注意最外一行/列常是分隔线或 1px 描边（§2.5）；
  - 浮点坐标在产物里会被取整，**取整方向**也会造成 1px 差异 → 校验给 ±1 容差，但**不能给更多**。

### 4.9 静默失效：写错了也不报错的值

- **现象**：产物和设计源不一致，但构建/校验一路绿灯；只有 **GUI 的工程检查**（如果它跑）
  偶尔报一句极简的错（如 `invalid color`），甚至什么都不报。
- **真因**：值在序列化时**丢了类型信息**（颜色 token 是整数 `0x2a3044`，
  写成 JSON 变成十进制字符串 `"2764868"`），消费端解析失败后**选择忽略**而不是报错。
  同类：字体名拼错 → 静默回退默认字号；图片名拼错 → 空白/占位；
  枚举值写错 → 取默认值。
- **通用解法**：
  1. 对每一类"错了也不会报错"的值，在**生成端**加白名单断言（颜色/字体名/资源名/枚举）；
  2. 报错要**点名到对象路径**并给出可操作提示（"少写了引号"比 `invalid color` 有用 100 倍）；
  3. **不要指望构建帮你拦** —— CLI 与 GUI 的校验范围经常不一致，
     而且"只在 GUI 报"的错在自动化流水线里等于不存在。
- **对号入座**：`cases/B6`；断言 A1（字体名列表）与 A10（颜色语法）。

### 4.10 坐标系：优先分层 + 相对换算，别轻易拍平

- **现象**：只有**嵌套在容器里**的控件偏移，顶层控件正常；容器里还多出一条滚动条。
- **真因**：子控件坐标以**父的边框盒**为基准：

  ```
  子绝对 = 父->coords.x1 + 子声明坐标 − 父->scroll_x
  ```

  - border / padding **不参与**（这点常被误以为要减，实测不用）；
  - **父的滚动量会叠加** —— 容器默认可滚动，子控件一旦溢出就把父撑出滚动区，
    滚动量把所有子控件一起带偏；
  - 超出父范围的部分**会被裁掉**（画了但看不见），所以要加「子控件不得越界」校验。

- **两种修法**（都能跑通，按维护性取舍）：

  | | 拍平（所有后代挂到页根） | 分层 + 相对换算 |
  |---|---|---|
  | 式子 | `渲染 = 声明` | `子绝对 − 父绝对` |
  | 父子语义 / 相对布局 / 成组移动 | 丢失 | 保留 |
  | 额外校验 | 无 | 子控件不得越界（否则被裁） |

  **默认选分层 + 换算**：语义正确、可维护。拍平只在框架不支持嵌套时用，
  或作为排障/对比模式。
- **对号入座**：`cases/B5`（含最终结论与实测数据）；与 §4.1 / §4.2 同族。

## 5. 标准作业流程（SOP）

### 场景 A · 改一处 UI（最常见）

```
1) 只改**设计源生成脚本**里对应的那一处
2) 生成设计源 → 跑自带自检（越界/换行/引用），必须 0 违规
3) 渲染设计预览图 → 目检
4) 转换进目标工程 → 跑校验（引用完整性、坐标非负）
5) 生成代码 → **再**生成资源（顺序不能反）
6) 交叉验证：产物渲染 vs 设计源渲染 → 逐像素差异应为 0
7) 原生验收：至少抓改动的那一屏，量化确认无结构性差异
```

### 场景 B · 只排查不修改

```
1) 抓原生渲染图（§3）
2) 跑 §2.6 六类体检（tools/tree_check.py + tools/ink_check.py）
3) 有差异 → §2.4 四步量化（tools/diff_report.py）→ §2.5 标定 → §4 对号入座 → cases/ 查历史
4) 输出「现象 / 证据（数值）/ 真因 / 建议修法」，不动任何文件
```

### 场景 C · 验收交付（批量抓全部页面）

```bash
for target in {ALL_TARGETS}; do
  {KILL_EXE}
  {启动（§3.2 参数）}; {等端口就绪}
  {抓 target → native/<target>.png}
done
# 自检：张数 == 目标数；唯一 md5 数 == 目标数（防重复图）
```

### 场景 D · 按设计稿批量生成整套 UI 并出图验收

```
1) 建"唯一设计源"生成脚本：设计 token + 每屏构造函数 + 布局助手
   （文本宽度/基线必须实测，别用系数估；见 §2.7）
2) 生成 → 跑生成端断言（越界/A1~A10）→ 0 违规才继续
3) 转换进目标工程：**组件树平铺 + 容器 pad 0**（§4.10）
4) 构建生成代码 → **断言产物清单齐全**（§4.7："成功"≠"有产物"）
5) 生成资源（字体/图片）→ 再断言一次总数（顺序不能反）
6) 接进 PC 仿真器：逐屏 load → 快照 → 写裸帧（§5.6）
   · 快照字节序按已知颜色标定后写成常量；缓冲不足就换堆或降位深
   · 出图模式结尾强制退出；调用端以"产物齐全"判成功
7) 与设计稿逐屏对照：切块差异 + 三联图（设计/实机/差异热力图）
8) 残留差异**归类**（渐变角度/阴影/发光/自绘图标这类"框架画不出"的），
   写进工程侧「已知差异」清单 —— 不要每次都重新排查
```

判据：差异图的残留应当是**稳定且可解释**的；出现"整块位移""整块缺失"就回到第 2~4 步。

### 6.1 图像差异量化

```python
def diff_report(ref_path, act_path, grid=40, big_thr=64, mid_thr=24):
    from PIL import Image, ImageChops
    from collections import Counter
    a = Image.open(ref_path).convert("L")
    b = Image.open(act_path).convert("L")
    size_ok = (a.size == b.size)
    if not size_ok:
        b = b.resize(a.size)          # 尺寸不一致要显式记录，别静默缩放
    dif = ImageChops.difference(a, b)
    hist = dif.histogram(); total = a.width * a.height
    big, mid = sum(hist[big_thr:]), sum(hist[mid_thr:big_thr])
    pts = [(x, y) for y in range(a.height) for x in range(a.width)
           if dif.getpixel((x, y)) >= big_thr]
    hot = Counter(((x // grid * grid, y // grid * grid) for x, y in pts)).most_common(8)
    return {"big": big, "mid": mid, "pct": 100.0 * big / total if total else 0.0,
            "hot": hot, "size_ok": size_ok}
```

### 6.2 墨迹包围盒 + 触边检查

```python
def ink_bbox(img, x0=0, y0=0, x1=None, y1=None, thr=140):
    x1 = x1 or img.width; y1 = y1 or img.height
    pts = [(x, y) for y in range(y0, y1) for x in range(x0, x1) if img.getpixel((x, y)) > thr]
    return None if not pts else (min(p[0] for p in pts), min(p[1] for p in pts),
                                 max(p[0] for p in pts), max(p[1] for p in pts))

def is_uniform_row(img, y, tol=2):
    """该行是否整行近似同色 → 通常是分隔线/底色，不是内容。"""
    first = img.getpixel((0, y)); lo = hi = first
    for x in range(1, img.width):
        v = img.getpixel((x, y))
        lo, hi = min(lo, v), max(hi, v)
        if hi - lo > tol:
            return False
    return True
```

### 6.3 组件树遍历断言（越界 / 引用完整性）

```python
def walk(node, page, issues, W, H, ax=0, ay=0):
    x, y = ax + node.get("x", 0), ay + node.get("y", 0)
    w, h = node.get("w"), node.get("h")
    if w is not None and h is not None:
        if x < -1 or y < -1 or x + w > W + 1 or y + h > H + 1:
            issues.append(("越界", page, node.get("type"), x, y, w, h))
    for c in node.get("children", []):
        walk(c, page, issues, W, H, x, y)

def collect_refs(root):
    """收集所有字体名 / 图片 / 跳转目标，用于引用完整性断言"""
    refs = {"fonts": set(), "images": set(), "links": set()}
    def go(n):
        f = n.get("font") or (n.get("style") or {}).get("font")
        if f: refs["fonts"].add(f)
        if n.get("texture"): refs["images"].add(n["texture"])
        if n.get("goto"): refs["links"].add(n["goto"])
        for c in n.get("children", []): go(c)
    for p in root.get("pages", []): go(p["screen"])
    return refs
```

### 6.4 文本真实宽度（居中/换行判定都要用它）

```python
class TextMeasurer:
    """按字符切换字体：图标私有区用图标字体，其余用正文字体"""
    def __init__(self, text_fonts: dict, icon_font=None):
        self.text_fonts = text_fonts      # {字号px: ImageFont}
        self.icon_font = icon_font
    @staticmethod
    def _is_icon(ch):
        cp = ord(ch)
        return 0xE000 <= cp <= 0xF8FF or 0x1F300 <= cp <= 0x1FAFF
    def width(self, s, px, with_margin=False):
        f = self.text_fonts[px]; w = 0.0
        for ch in s:
            ft = self.icon_font if (self._is_icon(ch) and self.icon_font) else f
            try: w += ft.getlength(ch)
            except Exception: w += px
        return w + (8 if with_margin else 0)   # 净宽用于居中；含余量用于换行判定
```

### 6.5 一键体检脚本骨架（把六类检查串起来）

```
for page in pages:

    文本宽 vs 框宽（6.4）          → 期望 0 处换行
```

## 7. 红线（通用 10 条）

1. **不要手改转换产物**（工程/生成代码）—— 只改设计源，重跑转换；产物要有自动备份。
2. **不要为"效果图"和"产品代码"写两套实现** —— 必然漂移。
3. **不要用"固定宽 + 对齐属性"做居中/右对齐** —— 序列化工具会重算；改成"content 宽 + 算出的坐标"。
4. **不要把图标码位混进正文字体的字符集** —— 会导致整份字体提取失败（正文一起坏）。
5. **不要用配置面板的字体度量做布局** —— 读生成物里的实际值。
6. **不要忘记清零默认主题的 padding/border** —— 否则"声明坐标 ≠ 渲染坐标"。
7. **不要在期望的构建步骤之前生成资源** —— 会被清理掉。
8. **不要忘记周期驱动事件/动画队列** —— 否则"点了没反应"。
9. **不要用肉眼判定"没问题"** —— 必须给数值证据（像素计数 / 墨迹包围盒 / 坐标比对）。
10. **不要把工程专属信息写进本工具箱** —— 工程差异只属于工程侧的配置文件；
    也不要静默缩放尺寸不一致的图做对比（会掩盖真实布局差异）。

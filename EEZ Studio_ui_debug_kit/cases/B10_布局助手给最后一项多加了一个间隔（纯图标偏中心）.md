# B10 布局助手给最后一项多加了一个间隔（纯图标按钮偏中心）

> 与 B9 同属「元素不在父正中」，但**机制完全不同**：B9 是居中没被声明，
> 本篇是**「间隔」的语义定义错了** —— 把「项与项之间的分隔符」写成了「每项后面的边距」。

## 现象

- 一类**只放了一个图标**的小胶囊按钮，图标不在正中：**左边空隙小、右边空隙大**
- 同一批页面里**带文字**的胶囊按钮完全正常（因为多了一项，把尾随间隔"吃掉"了）
- 偏移量恒定 —— 恰好是那个间隔常量的**一半**

## 证据

全量扫描 65 处「图标为父容器唯一子对象」，其中 6 处左右间隙不等：

| 页面 | 父尺寸 | 图标 | 左 | 右 | 差 |
|---|---|---|---|---|---|
| AiChat | 32×30 | 6×18 | 10 | **16** | 6 |
| Voice | 36×30 | 10×18 | 10 | **16** | 6 |
| History | 37×26 | 13×18 | 9 | **15** | 6 |
| NowPlaying | 32×28 | 6×18 | 10 | **16** | 6 |
| MusicLibrary | 43×30 | 15×18 | 11 | **17** | 6 |
| Notifications | 43×30 | 15×18 | 11 | **17** | 6 |

→ 全部是**恰好差 6**，而 6 正是布局助手的 `gap` 默认值。
→ 上下间隙是**相等**的（6/6、4/4、5/5），所以**只偏水平方向** —— 这是一条很强的定向线索：
  「某个水平方向的量多算了一份」，而不是两方向同比例错位（那是坐标换算，见 B5）。

## 曾经的误判

**误判：归因于左右内边距不对称。**
第一反应是去查 `pad_l / pad_r`。
→ 查完发现 6 处**全部是对称的**（10/10 或 11/11），且左间隙确实就等于 `pad_l`。
  内边距没问题 —— 说明多出来的那一份**在内容区内部**，是内容排版本身多算了一份。

**定向依据**：左右差 6 == 间隔常量，上下差 0 → 只可能是「水平排布时给最后一项也加了间隔」。

## 真因

布局助手在拼「点 + 图标 + 文字」时，给**每一项后面都无条件追加一个间隔**，
包括最后一项：

```python
# 错误：gap 被当成"每项后面的边距"
if icon:
    inner.append(sym(cur, …))
    cur += iw + gap          # ← 纯图标时，这条尾巴被算进了总宽
w = cur + pad_l + pad_r
```

于是总宽 = `图标宽 + gap + pad_l + pad_r`，而图标仍从 `pad_l` 起画。
左右各分到一份 padding，但**右边多了一份 tail gap** → 图标偏左 `gap/2`。

`gap` 的正确语义是「**项与项之间的分隔符**」（首尾都不该有），
就像 CSS flexbox 的 `gap` —— 它天然不含首尾。

## 修法

**只在「前面已经有内容」时才补间隔**，让纯单元素自然回到正中：

```python
if dot_col:
    inner.append(dot(cur + dr, h / 2.0, dr, dot_col))
    cur += dr * 2                      # ← 不再无条件 +gap
if icon:
    if inner:
        cur += gap                     # ← 只在项与项之间补
    iw = tw(CH[icon], icon_px)
    inner.append(sym(cur, …, icon, icon_px, fg))
    cur += iw                          # ← 不再无条件 +gap
if text:
    if inner:
        cur += gap
    inner.append(label_mid(cur, 0, h, text, px, fg))
    cur += tw(text, px)
w = cur + pad_l + pad_r
```

**为什么这是根治**：把「间隔」的语义从「每项后缀」纠正为「两项之间」，
于是「只有一项」「有两项」「有三项」三种情况都自动正确，不需要为纯图标情况打补丁。

副作用检查：`icon + text` 这类既有布局的**间距完全不变**（前项推进 `iw`，下一项前 `+= gap`，
结果还是 `iw + gap`）；只有纯图标胶囊变窄了 `gap`，且因为它通常是按返回值做右对齐，会自行跟随。

## 通用化

**"给最后一项也加了分隔符"是一类通用 bug**，任何手写排布的 UI 代码都会遇到。

| 栈 | 分隔符语义正确 | 容易写错的等价形式 |
|---|---|---|
| CSS | `display:flex; gap:6px`（首尾干净） | 每项 `margin-right:6px`，最后一项也留尾 |
| Flutter | `Row(children: separated)` / `Wrap(spacing:)` | 手写 `Row(children:[w, SizedBox(width:6)])` 多塞一个 |
| Android | `RecyclerView` ItemDecoration（系统管边界） | 每个 item View 自带 `marginEnd` |
| LVGL | flex flow + `pad_gap`（不含首尾） | 逐个 `set_x(prev + w + gap)` 并在最后也加 |
| Compose | `Arrangement.spacedBy(6.dp)` | 每项 `Modifier.padding(end = 6.dp)` |

**通用判别法（两步）**：

1. **看偏移量是否恰好等于某个间隔常量的一半**：是 → 几乎可以确定是尾随分隔符。
2. **看是否只有一个方向偏**：只有一个方向偏，说明多算的量来自**该轴的排布逻辑**，
   而不是整体坐标系（坐标系错会让两方向同比错位）。

**由此得到一条编写准则**：写「一批元素的自动排布」时，
永远遵守 **"间隔加在前一项与自己之间，而不是加在自己身后"**（等价于：
只有 `index > 0` 时才补间隔）。这条准则对所有手写布局、字符串拼接、日志格式化同理
（比如 `', '.join(parts)` 比 `for p in parts: s += p + ', '` 更不容易留下尾巴）。

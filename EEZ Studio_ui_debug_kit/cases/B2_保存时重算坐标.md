# B2 元素跑出画布边缘（保存时被重新居中）

## 现象

- 工程文件里某个标签的 `left` 变成了**负数**，渲染出来**文字跑到画布左边缘之外**
- 但**生成的代码里坐标是对的** —— 两者矛盾

## 证据

| 位置 | 值 |
|---|---|
| 设计源（手写的） | `x = 0`，宽 64，对齐方式 = 居中 |
| 目标工程文件（保存后） | `left = -13`、`width = 100` |
| 生成的代码 | 坐标是原始的正确值 |

三处不一致 → 说明**保存环节**动了手脚，而不是渲染环节。

## 曾经的误判

**误判为**："渲染器/编辑器有 bug。"

**实际**：编辑器**按它自己算的字宽重新做了居中**。给定的固定宽（64）比它算出的文本宽（约 38）大很多，
它把文本居中到框内时算出了负偏移。两边字宽算法不同（设计侧按整字号估，它按字形实际宽度）→ 偏。

## 真因

用「**固定宽度 + 对齐属性**」表达居中，等于把"定位权"交给了序列化工具。
工具在保存时按自己的度量重算，覆盖你的意图。

## 修法

**放弃对齐属性**，改成「**content 宽度 + 自己算出的 x**」：

```python
def centered_label(cx, base_y, text, size):
    # 净宽（不含防换行余量）用于精确居中
    w_net = measure_net_width(text, size)
    return label(x=cx - w_net / 2.0, width=CONTENT, align=LEFT /* 默认 */, ...)
```

这样工具**没有可重算的余地**：宽度随内容，位置由我们算死。

两个配套细节：
- 算**居中**用**净宽**；算**换行判定/右对齐余量**才用含余量的宽度
- 右对齐同理：`x = 右边界 - 净宽`

## 验证

```bash
python tools/tree_check.py                      # 期望 0 处越界 / 0 处折行
grep -c "set_pos(obj, -" <生成代码>             # 期望 0（负坐标计数）
python tools/ink_check.py <渲染图>.png --against L T W H   # dx/dy 应为 0
```

修复后：工程里负偏移 **0 处**；生成代码里负坐标 **0 处**。

## 通用化

| 栈 | 会不会重算 | 对策 |
|---|---|---|
| 可视化 IDE + 代码生成 | **会**（保存时按自己的字宽居中） | 用 content 宽 + 显式坐标 |
| 设计工具 → 代码插件 | 部分会（按 bounding box 重排） | 同上；或用绝对定位容器 |
| Android ConstraintLayout | 不会，但 `wrap_content` + `bias` 组合会 | 需要精确位置就用固定值 |
| Flutter | 不会（除非用 `Align/Center`） | 用 `Positioned` + 自己算的坐标 |
| Web | 不会，但 `text-align` + 固定宽会 | 同上 |

**通用判断**：只要出现"**设计源对、产物错**"，就优先怀疑**序列化/保存环节重算了布局**，
办法是把"可被重算的参数"（对齐、拉伸、自动宽度）换成"硬参数"（具体坐标、content 宽度）。

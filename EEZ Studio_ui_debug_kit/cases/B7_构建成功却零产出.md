# B7 构建报"成功"却零产出（产出清单被当成无用配置删了）

## 现象

命令行构建输出完整、且明确说没问题，但目标目录里**该生成的文件一个都没生成**：

```
Build project: .../test.eez-project
No error and no warning detected
EEZ Flow engine built
Build duration: 0.93 seconds
Build successfully finished at ...
```

目录里只有 2 个引擎文件，`screens.c` / `ui.c` / `styles.c` / `fonts.h` 等 10 个都不在。
而**同一个构建流程，在改动之前的工程上是正常产出 12 个文件的**。

## 证据

对比两次构建的日志行数（这是最快的定位手法）：

| 构建 | 日志里的关键行 |
|---|---|
| 正常 | `Configuration: Default` + `Compressed size: 12232` + 12 行 `File "…/xxx.c" built` |
| 零产出 | 以上 **13 行全部消失**，只剩 5 行通用收尾 |

`Compressed size` 和 `File ... built` 的缺失说明构建**根本没进入"产出文件"那一步**，
而不是"进入后失败了"。

## 曾经的误判

1. 先怀疑输出目录路径不对（相对路径 vs 绝对路径）—— 把 `destinationFolder` 改成绝对路径，
   **没有任何变化**，于是排除。
2. 再怀疑是新写的页面数据有问题导致构建短路 —— 把工程换回"只有一页一个标签"的最小
   版本，**依然零产出**，于是排除"数据问题"，锁定"工程配置被改坏"。

排除法的价值在这里：两次排除把范围从"数据/路径/代码"收缩到"**配置项**"。

## 真因

工程配置里有一个字段是**代码产出的清单表**（形如）：

```json
"settings": { "build": { "files": [
  { "fileName": "screens.h", "template": "…" }, { "fileName": "screens.c", "template": "…" },
  … 共 12 项 …
] } }
```

构建就是**按这张表逐项生成**的。我在"适配新版格式"时凭猜测把它当成历史遗留删掉了
（注释还写着"新版不再使用"），于是构建**没有任何要生成的东西**，
自然"零错误、零产出、光速完成"。

教训：**构建耗时异常短（0.9s vs 正常 1.3s）也是一个信号** —— 它什么都没干。

## 修法

1. 恢复该字段：改成"缺失时从随脚本存的备份 JSON 恢复"，而不是删掉：

```python
if not b.get("files"):
    b["files"] = json.load(open(os.path.join(HERE, "build_files.json"), encoding="utf-8"))
```

2. 顺手把输出目录写成绝对路径（虽然它不是本次的原因，但相对路径依赖 cwd，早晚出事）。
3. **给"零产出"加一条判据**：构建结束后检查期望文件是否都在，缺了就 fail；
   不要只看退出码和"成功"字样。

## 验证

```bash
python design/eez_build.py && ls src/ui
# 修复后：日志重新出现 Configuration / Compressed size / 12 行 File ... built
#         src/ui 下 12 个文件齐全
```

## 通用化

**"构建成功"≠"产物存在"**。任何 CLI 构建都要加产物清单断言：

- 记录**期望产物清单**（文件名 + 数量），构建后逐个 stat；
- 用**日志里的特征行**判断走到了哪一步（如 `File X built`），而不是只看 endpoints；
- 构建耗时与历史值差异过大（这里 0.9s vs 1.3s）时报警；
- 对"配置驱动的产出"（清单表 / 模板表 / 插件列表）：**不要凭"看起来像遗留"就删**，
  先做对照实验（把字段加回去，看行为是否恢复）。

同族坑：构建系统会把某些生成物（字体/图片）**只清理不重建**，于是必须"先构建、
后生成资源"（见 §4.7）。两者合起来，稳健做法是：

```
构建 → 断言产物清单 → 生成资源 → 再断言一次总数
```

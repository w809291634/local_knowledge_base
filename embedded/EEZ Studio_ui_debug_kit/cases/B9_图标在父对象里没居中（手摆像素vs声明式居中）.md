# B9 图标在父对象里没居中（手摆像素 vs 声明式居中）

> 同族：**B3**（默认主题 padding）、**B5**（子坐标相对父内容区）—— 三者都是
> 「父容器悄悄改变了子元素位置」。本篇专讲**「居中」这件事没有被声明出来**导致的偏移。

## 现象

- 圆形按钮里的图标**明显偏左**（不是差 1px，是差几十 px），但组件树里 `left/top` 看着完全正常
- 另一批圆形按钮里的图标**看着居中**，与编辑器里点「相对父对象居中」按钮的结果差 1px
- 同一个坑在不同页面上重复出现 —— 因为它们是**同一个辅助函数 / 同一种写法**批量产生的

## 证据

一次全量扫描：**65 处**「图标是父容器的唯一子对象」（= 意图就是在父里居中）。
其中 6 处左右间隙明显不等：

| 用例 | 父尺寸 | 图标 | 左间隙 | 右间隙 | 判定 |
|---|---|---|---|---|---|
| 纯图标胶囊 ×6 | 32×30 … 43×30 | 6×18 / 15×18 | 10~11 | **16~17** | 偏中心 3px |

另外两处是「手摆中心 + 事后覆盖」造成的**严重**偏移（不是 1px 级）：

| 用例 | 父（圆） | 写法 | 实际落点 |
|---|---|---|---|
| 聆听光球里的星形 | 112×112 | `sym(0,0,112,112)` 再覆盖 `x=int(round(ox-56))` | 覆盖进去的是**圆的左上角**，字形被推到圆的左边 |
| 暂停圆钮里的暂停 | 52×52 | `sym(0,0,52,52)` 再覆盖 `x=int(round(cx))` | 同上，字形偏左 |

「差 1px」那一批的精确证据（最重要的一个数字）：

```
播放按钮：父 32×32，字形 11×15
  EEZ 编辑器「相对父对象居中」→ left = 11, top = 9   （(32-11)/2 = 10.5 → 11）
  生成脚本用 Python round      → left = 10, top = 8   （(32-11)/2 = 10.5 → 10）
```

## 曾经的误判（四次，都值得记）

**误判 1：用 `text_align=CENTER` 求居中。**
以为「组件自带居中」就够了。
→ LVGL 单行 label 的 `text_align=CENTER` **只水平居中**，glyph 仍贴在框的**顶端**，
看着还是偏。此路不通。

**误判 2：以为 `sym(与父框相同的盒)` 已经「居中」就算完。**
它算出来的确是居中的，但**「居中」只是一个被算出来的坐标**，不是一个声明。
→ 父尺寸一改、或有人再补一次坐标，立刻漂；而且这种写法在几十个调用点里重复。

**误判 3（最关键）：把那 1px 归因于「量字形宽高不准」。**
起初认为是「Python 估的字形宽高 ≠ LVGL 真实渲染」。
→ 方向错了。真因是**舍入模式**：(32−11)/2 = 10.5，
**Python `round()` 是「.5 取偶」→ 10；编辑器的 JS `Math.round()` 是「.5 进位」→ 11**。
证据是拿编辑器里那个按钮的截图对照 —— 编辑器给的就是 11。

**误判 4：像素核对按「父尺寸」画大方框。**
以为在父中心附近裁一块去找白色字形就行。
→ 暂停钮下方正好是音量滑块的**白色圆点**，被一起算进质心，
报出 **17px 的假阳性**。必须按「子图标自身的包围盒 + 小边距」裁剪。

## 真因

两件事叠加：

1. **「居中」没有被声明，只是被算了出来。**
   组件树里 `left/top` 是绝对坐标，编辑器那两个「相对父对象居中」按钮（源码语义）
   也只是**当场算一次 `(父-子)/2` 写死**。所以没有人在运行时维持这个关系 ——
   一旦辅助函数手写恒坐标（还和被算好的 position 打架），偏移就无法自愈。
2. **生成脚本与编辑器的舍入模式不一致**：half-even（Python）vs half-up（JS），差 1px。

## 修法

**① 把「居中」变成一个可复用的声明**（而不是散落各处的坐标算式）：

```python
def center_in(child, parent):
    """等同于编辑器工具栏「相对父对象居中」那两个按钮。"""
    px, py = parent["x"], parent["y"]
    pw, ph = parent["w"], parent["h"]
    sz = fsize(child_px)                      # 子内容尺寸
    w, h = tw(child["text"], sz), lh(sz)
    # ★ 必须用 "half-up"，与编辑器的 JS Math.round 一致；
    #   Python 的 round() 是 half-even，(32-11)/2=10.5 会算成 10 → 差 1px
    child["x"] = int(px + (pw - w) / 2.0 + 0.5)
    child["y"] = int(py + (ph - h) / 2.0 + 0.5)
    child["w"], child["h"] = int(round(w)), int(round(h))   # 写回真实字形尺寸
    return child
```

调用方从此不再手摆像素：`parent["children"].append(center_in(icon("play", 13, WHITE), parent))`。

**② 顺手把「字形真实尺寸」写回节点。**
原来 content 尺寸的 label 没有 `w/h`，编译器会**兜底成 100×40** ——
虽然 content 单位下目标框架会忽略，但编辑器里的 rect 会显示错、
**它的居中按钮也会按错的尺寸算**。写回真值让两边一致，顺带让核验脚本能算出四边间隙。

**③ 清掉所有「手摆中心」的旧写法**，包括把 `sym(与父框相同的盒)`、
`sym(0,0,…)+事后覆盖 x/y` 这些形态统一换成 `center_in`。

**为什么是根治**：改完之后，「图标在父里居中」成了一条**可被机器校验**的性质
（四边间隙差 ≤1px），而不是靠人对着渲染图看。父尺寸一改，生成期自动重算。

## 验证

```bash
# 1) 结构性核对：列出全部「父容器唯一子对象」的居中情况
python build/verify_center.py
#    → 全部 65 处居中（左右/上下间隙差 ≤1px）

# 2) 像素质心核对（真渲染图上按子包围盒裁）
python build/verify_center.py --pixels
#    → 播放 0.74px、光球 0.32px、暂停 0.94px，全部 OK
```

配套要求：
- 判据是「**左右间隙之差 ≤1、上下间隙之差 ≤1**」—— 1px 是 half-up 取整的固有代价，不是 bug。
- **像素核对必须裁子包围盒**，不能裁父方框（见误判 4）。

## 通用化

这是**所有"由代码/数据生成界面"方案**的通病：居中只是个被算出来的数，不是被维护的关系。

| 栈 | 声明式写法（应如此） | 手摆像素（会漂） |
|---|---|---|
| LVGL | `lv_obj_center()` / `lv_obj_align(CENTER)` | `lv_obj_set_pos(x + (w-tw)/2, …)` |
| HTML/CSS | `display:flex; align-items:center; justify-content:center` | `top: calc(50% - 8px)` |
| Flutter | `Center(child: …)` / `Align(alignment: Alignment.center)` | `Positioned(top: (h-16)/2, …)` |
| Android | `ConstraintLayout` 双向约束 / `Gravity.CENTER` | 手写 `setX((w - tw) / 2f)` |
| SwiftUI | `overlay { Icon().frame(maxWidth:.infinity) }` | 手写 offset |

**两条跨栈硬规则**：

1. **凡是"某个元素应永远待在父正中"，就用一个中置的容器/约束表达它，不要手算半差。**
   手算出来的坐标一旦遇到「父尺寸变了 / 字体变了 / 有人二次赋值」就会漂，而且漂了没人报警。
2. **注意生成侧与宿主侧的舍入模式是否一致**（half-up vs half-even）。
   只要两边任一侧是 `.5`，就会稳定差 1px —— 而且这种 1px 极难凭肉眼归因，
   拿到**权威一侧的截图/数值**去对，是最快的定位手段。

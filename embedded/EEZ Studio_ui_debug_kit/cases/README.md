# cases/ —— 案例库

**这里是这个工具箱最值钱的部分。** 每解决一个非平凡问题，就追加一个案例文件。

## 为什么要写案例

同一个坑会在不同工程里反复出现（只是表现略有不同）。案例库让"下一次"变成**对号入座**，
而不是重新推理一遍。特别是**记录曾经的误判**比只留正确答案更有价值 ——
它能让后来者避开同一条弯路。

## 文件命名

```
B<序号>_<一句话现象>.md          例：B3_默认主题padding偏移.md
```

按发现顺序编号，不要重排（编号是引用锚点）。

## 必须包含的 7 段（模板）

```markdown
# B<n> <现象一句话>

## 现象
（客观描述：哪一类界面、哪个元素、什么表现。带上可复现的位置/尺寸）

## 证据
（数值！像素计数 / 墨迹包围盒 / 坐标比对 / 报错原文。没有数值证据的判断不算证据）

## 曾经的误判
（如果走过弯路，写清楚：误判成什么、为什么那样想、什么证据推翻了它。没有就写"无"）

## 真因
（一句话说清机制。要能解释"为什么表现是这样的"，而不只是"改了什么就好了"）

## 修法
（改哪个环节的哪一处；给出关键代码片段；说明为什么这样改是根治而不是打补丁）

## 验证
（用什么命令、什么数值，证明修好了。要能被别人复现）

## 通用化
（这个坑在别的框架/栈里对应什么？给出跨栈对照，方便迁移）
```

## 判据：什么值得写成一个案例

- 花了 **>30 分钟** 才定位的问题
- 有过 **≥1 次误判**的问题
- 根因属于某类**通用机制**（默认样式、异步、坐标系、字体资源…）
- 修复过程可以**脚本化/自动化**

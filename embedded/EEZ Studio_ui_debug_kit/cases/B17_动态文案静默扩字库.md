# B17 动态文案功能正确，却静默扩展 EEZ/LVGL 字体子集

> **检索别名**：动态中文 / 运行时文案 / 字体变大 / Flash 增长 / 字形预算 /
> `lvglGlyphs` / `ui_font_cn` / 状态提示豆腐字。

## 现象

在 EEZ no-flow 工程中给 native 状态层补“测量中”“已断开”“停止响铃”等动态提示。
为避免豆腐字，生成器把这些字符串加入字体收集列表；功能和画面都正常，但全部
`ui_font_cn*.c` 都变大，造成未审计的 Flash 增长。

## 证据

1. `collect_texts()` 决定工程写入 `lvglGlyphs` 的码位；EEZ 会为每个字号分别烘焙子集。
2. watch 工程加入运行时文案后，生成器报告的码位数从 **302 → 310**；删除后回到 **302**。
3. 通过 EEZ 官方提取器重烘后，11 个 `ui_font_cn*.c` 与基线 Git blob 哈希逐一相等。
4. 文案改为既有中文或 ASCII 后，PC_SIM 功能与导航回归仍为 **61 PASS / 0 FAIL**。

## 曾经的误判

“动态文案只多几个字，先加进字库最稳”。这会忽略同一字形可能在多个字号重复烘焙：
功能测试看不出问题，Flash 账单却被悄悄放大。

## 真因

字库并不按“字符串数量”计费，而是按**字体档位 × 唯一码位**烘焙。native 代码中的新文案
若没有被设计源收集，显示会缺字；若无差别加入收集列表，又会把新增字形复制进相关字号。

## 修法

按优先级处理动态文案：

1. 优先复用设计源已收录的中文词（例如“开始”“暂停”“测量”）；
2. 状态码/调试态优先使用 ASCII（如 `BLE OFF`、`...`、`||`）；
3. 只有产品文案不可替代时，才把它加入设计源的收集列表，并记录涉及字号、码位增量和 Flash 增量。

绝不在 native C 中新增中文后只靠“重新烘字库”掩盖成本。

## 验证

```text
生成器码位：310 → 302
for every ui_font_cn*.c: hash(worktree) == hash(baseline)
PC_SIM：61 PASS / 0 FAIL
```

## 通用化

- Web：动态国际化字符串会增大分包/字体 subset；先复用 token，再审批新文案。
- Android/iOS：动态资源可能拉入整段 Unicode fallback 字体；不能只看 APK 是否能编过。
- 嵌入式：把“新增可见字符”视为资源变更，而非普通逻辑改动；代码评审应同时检查字号覆盖与 Flash 账单。

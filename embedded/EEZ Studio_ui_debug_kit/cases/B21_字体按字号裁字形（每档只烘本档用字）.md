# B21 字体按字号裁字形（每档只烘自己用到的字，Flash 10.8MB → 1.7MB）

> **检索别名**：字体太大 / Flash 吃紧 / 字体档 / lvglRanges / lvglGlyphs / 字库裁剪 /
> subset / 字形预算 / 未用字体 / 省内存 / runtime_text / 豆腐字。
>
> 与 [B17](B17_动态文案静默扩字库.md) 配套：B17 讲"别让动态文案悄悄撑大字库"，
> B21 讲"反过来，主动把每个字号压到只剩它真正需要的字形"。**字体的默认实现必须按这里做。**

## 现象

EEZ no-flow 工程（25 屏 / 11 个字号档）编译出的字体占 **约 10.8 MB**：

- 单档最大 `ui_font_cn76.c` **3.33 MB**，而这档实际只显示"10:09"这种数字；
- 11 档 `ui_font_cn14…cn76` 的 `lvglRanges` **完全相同**（同一份 311 码位）；
- 每多一个字号，就再复制一份"全工程字形"，Flash 直接按档位翻倍。

## 证据

1. 生成器（设计源 → `.eez-project`）把**全工程码位的并集**写给每一个字号：

```python
codes = set(range(32, 127))
for t, _px in texts:
    codes.update(ord(c) for c in t)      # ← 所有文字，不分字号
ranges = ["32-126"] + [str(c) for c in sorted(codes) if c > 126]
for px in sizes:
    fonts.append({..."lvglRanges": ",".join(ranges)})   # ← 每档都写同一份
```

|---|---|---|---|

| cn64 | 6 | 数字/度号 | 2.37 MB |
| cn52 | 6 | 数字 | 1.60 MB |

3. 烘焙期还暴露一个**一直存在的豆腐隐患**：`FAIL: Font "simhei.ttf" doesn't have any
   characters included in range 0x25b6-0x25b6` —— native 写的播放符号 `▶`(U+25B6)
   在 simhei 里根本没有，之前只是没被收集到，真机上就是空框。

## 曾经的误判

1. **"11 档都在用，所以没有可删的字体"** —— 对，档位不能删；但**每档里的字形**绝大多数
   用不到。成本单位是「档 × 字形」，不是「档数」。
2. **"按字号裁字会缺字，太冒险"** —— 缺字风险真实存在，但只出现在 **native 运行时改写
   label 文案**的那几个控件；把这几个控件的运行文案在**同一字号**声明出来即可闭环。
3. **"动态文案全量加进所有档最稳"** —— 就是 B17 的坑：功能对了，Flash 悄悄翻倍。
4. **"用符号字（▶/⏸）更好看"** —— simhei 没有这些码位，烘焙直接报错或静默空框；
   要用就得先确认字体有该码位，否则一律 ASCII（`>`、`||`）。

## 真因

LVGL/EEZ 的字体是**按「字号档」各自独立烘焙的位图字形表**：

```
Flash ≈ Σ(每个字号档 × 该档烘焙的码位数 × 该档单字面积 × bpp)
```

生成器给每档都写全量码位时，上式第一项被乘满，于是小屏上最贵的大字号（76px）
反而背了 300 多个它永远不显示的中文字形 —— 单档就 3.3 MB。

## 修法（本工程的定稿做法，直接照抄）

### 1) 生成器：按字号收集字形

```python
def build():
    texts = collect_texts()                      # [(文案, 字号)]
    # 每个字号只取"该字号真正会显示的字"；ASCII 32-126 作基线
    # （native 的数值/英文文案在任何档都可能出现）
    per_size = {}
    for t, px in texts:
        per_size.setdefault(bucket(px), set()).update(t)
    sizes = sorted(per_size)

    def size_glyph_table(chars):
        codes = sorted(ord(c) for c in chars if ord(c) > 126)
        return ["32-126"] + [str(c) for c in codes], \
               [{"from": 32, "to": 126}] + [{"from": c, "to": c} for c in codes]

    for px in sizes:                              # ← 每档写自己的 ranges/encodings
        ranges, encodings = size_glyph_table(per_size[px])
        ... "lvglRanges": ",".join(ranges), "lvglGlyphs": {"encodings": encodings}
```

### 2) 设计源：native 运行文案用 `runtime_text` 声明（只在该字号付代价）

```python
# 控件自己显示的是"开始运动"，但 native 运行时会改写成"暂停"：
{"type": "pill", "id": "sp_start", "text": "开始运动", "runtime_text": "暂停", ...}
```

```python
def collect_texts():
    texts = []

    def add(w, text, px):
        texts.append((text, px))
        if w.get("runtime_text"):                # ← 并入同一个字号，不污染其它档
            texts.append((w["runtime_text"], px))
    ...
```

本工程需要声明的地方（一次性梳理完，之后新增同类控件照做）：

| 页面 | 控件 | 设计文案 | runtime_text | 说明 |
|---|---|---|---|---|
| app_sport | sp_start | 开始运动 | 暂停 | 运行/暂停切换 |
| app_stopwatch | sw_start | 开始 | 暂停 | 同上 |
| app_timer | tm_pause | 暂停 | 继续 | 暂停/继续切换 |
| app_spo2 | so_measure | 测量 | 开始 | 测量中按钮文案 |
| app_music | t0 | 夜曲 | 晴天稻香 | 三首曲名轮换 |
| app_music | t1 | 周杰伦 · 十一月的萧邦 | 叶惠美魔杰座 | 专辑名轮换 |
| app_calc | t0 | 128 | -.e | 负数/小数/科学计数 |

### 3) 字体没有的符号 → 换 ASCII，而不是硬加码位

```c
/* simhei 没有 U+25B6：播放态用 ASCII ">"，与设计源控件字形一致 */
set_text(objects.app_music_b_app_music_mu_ctrl_g1_t_l,
         watch_model.music_playing ? "||" : ">");
```

### 3b) 数据表驱动的 native label 也必须按档收集（否则只有那一档变豆腐）

有些控件的文字**在设计源里根本没有 label**——整块由 native 建（例如 applist 滚轮行：
设计源只声明"滚轮宿主"，14 行 icon+名称都是 native 创建，行名字号固定 `ui_font_cn14`）。
按字号裁字形后，这一档缺字就会只在运行态出现豆腐（设计图看不出来，因为设计图是 Python 渲染）。

```python
elif t == "roller":
    # 滚轮行全部由 native 建，行名字号 ui_font_cn14（watch_list_native.c）；
    # 设计源这里没有 label，必须显式按 14 收集，否则该档缺字变豆腐。
    for name, _color, _glyph in w["apps"]:
        add(w, name, 14)
```

**规则**：凡是 native 自建 label 且字号写死的控件，都要在生成器里补一条"按该字号收集"，
并写清字号出处（`xxx.c` 里的 `ui_font_cnNN`）。这条和 `runtime_text` 是同一件事的两种形态：
- 设计源里有同名 label → 用 `runtime_text` 补运行文案；
- 设计源里压根没有 label → 必须在 `collect_texts()` 里按 native 使用的字号补数据。

### 4) 烘焙后做"字形存在性"核对（别只看体积变小）

每档稀疏表的 `range_start` **不一样**（实测 cn18=183、cn16/cn20=176、cn26=19982），
校验脚本必须逐文件读 base，不能写死：

```python
import io, re
need = {18: "暂停继续开始", 20: "暂停", 26: "晴天稻香", 16: "叶惠美魔杰座"}
for px, chars in need.items():
    s = io.open("src/ui/fonts/ui_font_cn%d.c" % px, encoding="utf-8", errors="ignore").read()
    base = int(re.findall(r"\.range_start = (\d+), \.range_length", s)[1][0])
    block = s[s.index("unicode_list_1[]"):]
    block = block[:block.index("};")]
    vals = {int(x, 16) for x in re.findall(r"0x([0-9a-fA-F]+)", block)}
    assert all(ord(c) - base in vals for c in chars if ord(c) > 126), px
```

## 通用化

**成本模型**：字体 Flash ≈ Σ(档 × 档内码位 × 单字面积 × bpp)。省内存的次序永远是：

1. **减档**：能不新增字号就不新增（同义字号合并、就近取档）；
2. **减字**：每档只烘本档用到的字形（本文核心；大小字号收益最大）；
3. **减位深**：4bpp → 2bpp（小字号）、必要时 1bpp；
4. **符号先行**：先查字体是否有该码位，没有就用 ASCII/自绘，别硬加（emoji/▶ 之类）。

跨栈对照：

| 栈 | 对应机制 | 同样要做的两件事 |
|---|---|---|
| Web | `@font-face` subset / unicode-range | 每字重每字号单独 subset；动态文案单独审批 |
| Android/iOS | 自定义字体子集 / 系统 fallback | 别依赖 fallback（体积不可控）；构建后统计字体资产字节 |
| 嵌入式 LVGL/EEZ | `lvglRanges` + `lvglGlyphs` | 生成器按档收集 + 运行文案按档声明 + 烘焙后体积门禁 |

**门禁建议**（可以直接进 CI）：烘焙完成后打印「档 × 字节」表格，总字节超过预算即失败；
同时跑一次"runtime 字形存在性"断言，避免为了省内存反而出现豆腐字。

# B5 嵌套容器的子控件二次偏移（文字跑到卡片外、卡片里只剩滚动条）

## 现象

绝对坐标的设计源编译进目标工程后，**嵌套容器里的子控件全部不在原位**：

- 卡片内部几乎是空的，只在右边缘多出一条细长的滚动条；
- 本该在卡片里的文字/图标，出现在画布下方或卡片之外；
- 顶层（直接挂在页根下的）控件位置却是对的。

复现位置：一张 688×104 的渐变卡片，内部放了「光晕 + 图标底板 + 三行文字 + 两个胶囊」，
坐标全部按 800×480 画布算好。

## 证据

改前改后各跑一次仿真器截图，同一份设计源：

| | 卡片内可见元素 | 说明 |
|---|---|---|
| 保留嵌套 | 1 条滚动条 + 1 个孤立冒号 | 子控件被累加了父容器位置 |
| 平铺 | 全部 8 个元素各就各位 | 与设计稿结构一致 |

量化：卡片自身的 `lv_obj_set_pos(obj, 94, 188)` 正确；其子标签在生成代码里是
`lv_obj_set_pos(obj, 172, 220)`，实际渲染落到 `(94+172, 188+220) = (266, 408)` ——
已经掉出卡片（卡片底边 292）。

## 曾经的误判

先怀疑「字体没烘焙 / 文本是空的」，因为看起来"文字不见了"。实际文字都在，
只是被画到了画布外；换个角度看一眼截图就能发现底部区域多了一堆文字。

## 真因

**目标框架里，子控件坐标是相对「父对象内容区」的，而设计源写的是画布绝对坐标。**

```
渲染坐标 = 父的渲染坐标 + 子声明坐标 − 父的 border − 父的 padding
```

只要有多层嵌套，这条式子就会叠加多次。而父容器的内边距还未必是你写的 ——
默认主题会给容器/按钮加内边距，等于又加了一项未知量（见 §4.2 / B3）。

## 修法

**别做「绝对 → 相对」换算，直接平铺**：把所有后代提升成页根的直接子节点，
先序（父先于子）即原绘制顺序，z 序天然正确。

```python
def flatten_screen(screen):
    flat = []
    def walk(node):
        kids = node.get("children") or []
        node["children"] = []      # 断开嵌套
        flat.append(node)
        for k in kids:
            walk(k)
    for k in list(screen.get("children") or []):
        walk(k)
    screen["children"] = flat
```

配套两条：

1. **所有容器显式 `pad_*=0`** —— 把"父内容区"钉死成"父的矩形"，未知量归零；
2. 非点击控件（标签、装饰块）保持 `clickable=False` —— 平铺后它们盖在按钮之上，
   可点击的话会把按钮的点击吃掉（D7）。

为什么是根治：平铺之后式子退化成 `渲染坐标 = 页根坐标(0) + 声明坐标`，
不存在可以累加的项，也不再受父容器样式影响。

**代价**：失去父容器的裁剪（内容溢出不会被裁掉）。若确实需要裁剪，
只对那一块保留一层嵌套，并把它自己的 `pad_*` 显式写 0。

## 验证

```bash
python design/json2eez.py     # 编译（会打印页面数）
python design/sim.py --ui-only
python design/compare.py      # 与设计稿逐屏差异
```

判据：卡片区域内**可见元素个数**与设计源一致；差异图上大片「整块位移」消失，
只剩文字/图标字形级别的差异。

## 通用化

任何「声明式组件树 + 绝对坐标设计源」的栈都会遇到：

| 栈 | 子坐标基准 | 对应做法 |
|---|---|---|
| LVGL / EEZ | 父内容区（减 border/padding） | 平铺 + 容器 pad 0 |
| HTML / CSS | 最近的 positioned 祖先 | 子元素 `position:absolute` 时注意父级是否 `position:relative` |
| Flutter | Stack 内部相对 Stack | 多层 Stack 会叠加，`Positioned` 要按最内层算 |
| Android View | 父的 padding 之后 | `layout_margin` 与父 padding 会叠加 |

一句话：**要么统一用绝对坐标并平铺，要么老老实实做逐层换算 —— 不要两套混用。**

---

## 补充（后续实战修正：最终选了"分层 + 换算"，平铺只作排障用）

上面给的修法是**平铺**。后来又遇到一次真实反馈 ——
「每个子对象都是并列关系，没有父子关系，也不是相对布局」：
平铺虽然能消掉偏移，但**组件树退化成几百个平级节点**，
父子语义、相对布局、成组移动（在编辑器里把一张卡片整体挪走）全部丢失。
于是改回**分层 + 相对坐标换算**，并把规则查到了源码级：

```c
/* LVGL 9.4 src/core/lv_obj_pos.c :: lv_obj_move_to */
x += parent->coords.x1 - lv_obj_get_scroll_x(parent);
```

三条结论（推翻了本文原先"要减父 padding/border"的猜测）：

1. `coords.x1` 是父的**边框盒**原点 —— **border / padding 都不参与**换算，
   所以只需要 `子绝对 − 父绝对`；
2. 但**父的滚动量会叠加** —— 容器默认 `SCROLLABLE`，子控件一旦溢出，
   父被撑成可滚动，`scroll_x/y` 把所有子控件一起带偏。配套：
   容器/按钮去掉 `SCROLLABLE` + 保证不溢出（双保险）；
3. **子控件超出父范围会被裁掉**（画了但看不见），所以要加一条生成端校验：
   「子控件必须在父的矩形内」。这条校验一次就抓出 4 类真实问题：
   电池电极在主体之外、气泡头像超出、滑块的圆点比轨道高被削平、分区指示条贴在栏外。

两者对比（都能跑通，选哪个取决于你更在乎什么）：

| | 平铺 | 分层 + 换算 |
|---|---|---|
| 坐标式子 | `渲染 = 声明` | `子绝对 − 父绝对`（+ 注意父滚动） |
| 父子语义 | 丢失 | 保留 |
| 相对布局 / 成组移动 | 不行 | 可以 |
| 排版改动成本 | 改一处不影响别人 | 改父要连带看子 |
| 需要额外校验 | 无 | 子控件不得越界（否则被裁） |

**结论：默认用分层 + 换算；平铺保留为排障/对比模式（`--flat`）。**
验证方式不变：换布局模式后重跑逐屏对照，差异**不上升**就说明换算正确
（本次实测：平铺 8.30% → 分层 8.14%，反而略优，因为滑块圆点不再被裁）。

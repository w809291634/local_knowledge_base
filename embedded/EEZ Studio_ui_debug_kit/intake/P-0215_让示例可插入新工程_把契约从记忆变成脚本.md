# P-0211 · 让示例"可插入新工程"：把契约从记忆变成脚本

- **工程**：app-wifi-scan-conn-no-flow
- **日期**：2026-10-25
- **工具**：Qoder
- **状态**：fixed
- **标签**：可移植性,契约,自检脚本,模块化
- **关联提示词**：PR-0385

## 现象（看到什么）

用户问"怎么快速适配新工程、直接模块化插入"。实际盘点发现：代码本身可搬，
但**插入成本全在三份靠人记的契约**——EEZ 对象名（11）、native 动作（6）、平台接口（9），
外加 lv_conf 的 4 个开关；漏任何一个都是链接错或运行期空指针。

## 复现（怎么稳定重现）

把模块拷到一个缺 `btn_refresh` 或 `wifi_disconnect` 动作的新工程：编译能过（对象是结构体成员），
运行到刷新/断开时才炸；排查要翻 3 个文件。

## 根因（真正的原因）

契约散落在代码引用里，没有"一份可执行的清单"；新工程只能靠读代码或问人。

## 修复（做了什么）

`design/port_check.py`：读目标 `screens.h` 的 `objects_t`、`actions.h` 的声明、
本工程 `wifi_platform.h`、`lv_conf.h`，缺项直接点名并 rc=1；写进 `PORTING.md`（五步 + 契约表）。
同时做两处零开销集中化：`app/wifi_text.h`（文案）、`widgets/wifi_skin.h`（皮肤）。
（另两项——真接口 profile 缓存与"夹具原语拆 harness.h"——首次提交后被用户否决并还原，
理由是对内存有顾虑；见 PR-0386。）

## 证据（数字 / 命令输出）

`PORT CHECK PASS`（11/11、6/6、9/9、4/4）；缺 9 个对象 + 5 个动作的假工程 → rc=1 并逐项列出；
`PREFLIGHT PASS`、`[NAV] 64/0`。

## 沉淀（新增断言 / 案例 / 文档）

**"可复用"的判据不是代码能搬，而是"目标工程缺什么能一条命令说出来"**：
把契约写成脚本，比写十页移植文档可靠；脚本同时给出改动的单一真值点（文案/皮肤/夹具原语）。

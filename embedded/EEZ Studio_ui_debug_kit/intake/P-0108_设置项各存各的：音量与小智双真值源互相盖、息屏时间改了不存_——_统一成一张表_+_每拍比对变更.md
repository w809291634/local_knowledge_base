## 追加（同日 22:0x）：统一表上线后用户实测「拖音量又弹回 70%」⇒ tick 三步的顺序是硬性的

真机反馈：拖动主音量滑杆，滑杆动了但马上回到 **70%**。70 正是 `audio_codec.h:54` 的
`output_volume_ = 70` —— 一眼指向"硬件旧值把表顶回去了"。

**根因 = 我把 tick 写成「读回 → 输出」。** 一拍里先读硬件（还是 70）把表改回 70，
用户那一拍的 30 就永远落不到硬件上。顺序必须反过来：**输出 → 读回**
（刚写进去的值读回来与表相等，不会互相顶）。

**顺带发现的第二个坑（开机倒灌）**：真机音量是 codec 自己在 `Start()` 里从它的 NVS 恢复的
（`audio/audio_codec.cc:29-36`）。如果第一拍就把我们表里的默认值写出去，等于**把用户上次
存的音量顶成默认**。⇒ 加门槛 `s_vol_pulled`：**成功读回硬件之前，一次都不往外写音量**；
读回成功时顺手把 `applied` 影子对齐，省掉"刚读到又写回去"的多余一次 codec 调用。
没有读回能力的项（背光）不受影响，第一拍照常落硬件。

**回归自证 = 新增走路脚本 `--walk=volpull`**：进音乐页 → 读百分比 label → `setslider 30`
→ 等 700ms（过几十拍）→ 再读 → 必须仍是 30 → 再拖 55 重复一次。

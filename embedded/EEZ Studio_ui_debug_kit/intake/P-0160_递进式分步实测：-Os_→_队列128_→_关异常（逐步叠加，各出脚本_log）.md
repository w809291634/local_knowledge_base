# P-0160 · 递进式分步实测：-Os → 队列128 → 关异常（逐步叠加，各出脚本 log）

- **工程**：p4_touch_lcd4_3_exp/lvgl_demo_template
- **日期**：2026-10-19
- **工具**：Trae
- **状态**：fixed
- **标签**：EEZ,递进实测,分步优化,-Os,执行队列,CXX异常,eh_frame,flash,RAM,ui_size_report,边际收益
- **关联提示词**：PR-0276

## 现象（看到什么）

需要「一项项递进」的边际收益：先只加 size 优化(-Os)，再叠加队列，最后叠加关异常，看每步各贡献多少。

## 复现（怎么稳定重现）

从同一基线出发，每步只在上一步基础上加一项，各构建一次并跑 tools/ui_size_report.py 抓 log；步骤0 未优化 → 1 +ui -Os → 2 +队列128 → 3 +关CXX异常RTTI。

## 根因（真正的原因）

三项作用点互不重叠：-Os 压引擎代码密度（同时把 .eh_frame 从 36.9KB 降到 29.7KB）；队列是静态 bss 数据（每项12B，不动代码）；关异常删掉整套 EH 运行时（.eh_frame→0、libgcc unwind、libstdc++ EH/typeinfo）。故边际收益可加，且顺序不影响总量。

## 修复（做了什么）

无（分步度量）。

## 证据（数字 / 命令输出）

单位 KB(1KB=1024B)，括号为精确字节。\n步骤0 未优化：bin 1,143,488 / 链接后 1,142,430 / RAM 202,224 / 引擎 216.8KB(222,006) / C运行时 29.6KB / .eh_frame 36.1KB(36,916)\n步骤1 +ui -Os：bin 1,063,472 / 1,062,465 / RAM 202,224 / 引擎 138.7KB(142,006) / 29.6KB / 29.0KB(29,732)\n步骤2 +队列128：bin 1,063,472 / 1,062,435 / RAM 191,760 / 引擎 138.7KB / 29.6KB / 29.0KB\n步骤3 +关异常/RTTI：bin 991,024 / 990,092 / RAM 191,367 / 引擎 92.4KB(94,668) / 5.9KB / 0\n逐步增量：①-Os → flash -79,965(bin) / RAM 0；②队列 → flash -30 / RAM -10,464(202,224→191,760，bss 20,973→10,509)；③关异常 → flash -72,448(bin) / RAM -393。合计 flash -152,464（-13.3%）、RAM -10,857。结论：flash 收益主要来自①-Os(-80KB) 与③关异常(-72KB)；RAM 收益全部来自②队列(-10.5KB)。

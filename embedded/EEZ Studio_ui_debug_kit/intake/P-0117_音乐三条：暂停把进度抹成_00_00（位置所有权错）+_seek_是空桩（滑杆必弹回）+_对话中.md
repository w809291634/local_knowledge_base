- **日期**：2026-10-07
- **工具**：Qoder

## 现象（看到什么）

P-0116 之后真机三条残留：①AI 对话中（已唤醒）点播放键，对话被退出、UI 落到「休眠中」，云端还回一句「拜拜」TTS；②正在放歌时被唤醒打断，进度条被弹回 00:00；③播放中拖动进度条，声音不跟着跳（滑杆松手后自己弹回原处）。

## 复现（怎么稳定重现）

②③：design/sim.py 走路脚本 npyield（ai 2 抢占后 gettext m_np_prog_time）与 npseek（mouse 点滑杆 74% 处 -> gettext m_np_prog_time）。①只能在真机复现，PC 没有对话可退；已核对全工程只有 BOOT 按钮（board_p4_audio.cc:107-118）会调 ToggleChatState，UI 侧没有任何通往对话状态的路径。

## 根因（真正的原因）

②③同源：位置的所有权放错了地方。io_music_player_position() 写成 `if (!s_playing) return -1;`，把「位置」当成「在播」的附属品，于是 io_esp 一发到 -1 就 `s_progress = 0` 并把时间文本刷成 00:00（io_esp.cpp:781-784，注释还自称是防假反馈），任何一次暂停（含 AI 抢占）都把进度抹掉。③是 io_music_seek 从头到尾是 TODO 空桩（io_esp.cpp:1362），而滑杆是真控件：拖动发出 APP_OUT_MUSIC_SEEK -> 空桩什么都不做 -> 下一拍又被旧位置刷回去，看起来就是弹回。①未定论：UI 里没有任何代码能结束小智对话（voice_stop 是孤儿动作、没绑控件），而「休眠中」这一格的判据是 `!s_wifi_up`（io_esp.cpp:478）—— 显示成休眠说明那一下网络判定掉了，云端因此断掉音频通道并回一句再见。首要嫌疑是 P-0115 那一族：对话中再叠一趟「开文件 + 解码 + 写同一颗 codec + SD 读」，把 esp_hosted 的 SDIO / 内部 DMA 压垮。等真机日志定案（取证清单在「沉淀」第 5 条）。

## 修复（做了什么）

②位置改成播放器的事实，不再挂在「在播」上：新增 s_pos_pct（停在文件的百分比）+ s_pos_idx（这个位置属于哪一首），io_music_player_position() 的判据从 `!s_playing` 改成 `s_pos_idx < 0` —— 只有「没这首歌」（没播过 / 放完 / 卡被换空）才返回 -1。换下标才清零，同一首停了再播是从原处续。另外 io_music_rescan() 开头补 io_music_player_forget()：卡一换，同一个下标是另一首歌，位置账必须作废。
③真跳转：mp_req_t 加 seek_pct（-1=无请求），io_music_player_seek(pct) 投请求 + 当场把 s_pos_pct / s_pos_sec 记上（滑杆松手就是对的，不等任务）；播放任务的 apply_seek 按 `file_size * pct / 100` 折算字节 fseek，解码器没有 seek API => 关掉重开，让 parser 从新位置找帧头，重采样器随首块 PCM 重建（src_rate 归 0 复用既有触发），dst_frames_done 按新秒数重算，进度就接得上。开新曲那段也调它：暂停后拖过 / 续播都先跳回去。
①的规避（同时消掉 P-0116 遗留的「闪一帧播放」）：新增 ai_owns_audio()（= 聆听或回复），io_music_play_pause / select / prev / next 四条命令在它成立时直接 return —— 不投播放请求、不改意图，也就完全不碰 codec / SD / I2S；io_pc 同一条规则镜像。

## 沉淀（新增断言 / 案例 / 文档）

1) 位置/进度这类事实归硬件那侧所有，暂停只是「没在推进」，不是「没有位置」。getter 写成 `if (!running) return -1;` 是最容易顺手做出的错：它让每一次暂停都顺手清掉 UI 的显示，而 UI 还以为自己在防假反馈。判据应该问「还有没有这首歌」，不是「现在有没有在跑」。
2) 空桩 + 真控件 = 必然的弹回：滑杆/开关这类双向控件一旦绑上，命令侧留 TODO 就等于承诺了一个不会发生的动作；要么先把控件收起来，要么同批把命令做掉。
3) 解码器没有 seek API 时的通用做法：按「字节 ∝ 时长」折算目标位置 -> fseek -> 关掉重开 -> 让 parser 自己找帧头（本工程另有「零前进就丢字节」的兜底）。代价要当场说清：WAV 折算精确，MP3 定码率准、变码率有百分之几误差且落点不在帧头上（可能先丢半秒声音）—— 这是免索引方案的固有代价，不是 bug。
4) 「点 A 结果 B 被干扰」这类跨子系统问题，先把自己这侧的调用图查干净再谈玄学：本工程全量 grep 只有 BOOT 按钮（GPIO35）会 ToggleChatState，voice_stop 是没绑控件的孤儿动作 => UI 不可能主动结束对话；再对照「休眠中」= `!s_wifi_up` 这一格判据，方向就落到网络 / DMA 负载上。既别把「我们没写过的路径」当成「不会发生」，也别反过来赖硬件 —— 用日志判。
5) 取证清单（①待用户日志）：`ai state: 2 -> 0 (phase=? wifi_up=?)` 一行就能分流 —— `wifi_up=0` = 网络判定掉了（P-0115 SDIO / 内部 RAM 那一族）；`phase=1 wifi_up=1` = 小智真的回了空闲。同时看 esp_wifi 断连原因、esp_hosted / mempool / ESP_ERR_NO_MEM、application 的音频通道关闭，以及新加的 `music: AI 对话中，播放/暂停忽略（不退对话）` 在不在（证明烧的是这一版）。

### ①的新改法：静默结束对话 + 照做动作

板级桥 `main/board_p4_audio.cc` 新增 `app_ai_end_conversation()`：只在
Listening/Speaking 时调 `Application::ToggleChatState()` —— 走 BOOT 按钮同一条出口
（`application.cc:695-710`：Listening -> `protocol_->CloseAudioChannel()`，
Speaking -> `AbortSpeaking()`）。
★ **不走 `Application::StopListening()`**：它发 `{"type":"listen","state":"stop"}`
（`protocol.cc:71-74`），小智服务端收到这句会回一段告别 TTS —— 用户要免掉的"拜拜"就是它。
关通道是本地结束会话，服务端没机会回话。
配套：`io_esp.cpp` 加 3 秒宽限窗口（`s_ai_exit_at_ms` / `ai_exit_in_grace()`）。
必要原因：`s_ai_state` 是工作任务 200ms 采一次，而主循环真关完还要一两百 ms，
"结束对话 + 开播"是同一拍做的；没宽限，下一拍采到 2/3 就把刚要播的歌暂停掉（表现＝点了没反应）。

### ②进度条"来回飘 + 时间不准"的三处来源（不是一处）

1. **总时长是设计稿字面量**：`build_ui.py` 里那格 "03:58" 从来没绑变量 ⇒ 放哪首都显示 03:58，
   和左边当前时间自然对不上。改成绑 native 输入 `music_time_all`（真机取播放器估算，
   估不出来显示 `--:--`；仿真假歌就发 03:58，所以 G5 对照图不变）。
2. **派生值被算了两次**：UI 侧原来用 `pos*100/dur` 自己折算百分数，而播放器内部另有
   `s_pos_pct`；两次整数除法的舍入差 1%，每拍刷一遍就是飘。改成播放器直接给
   `io_music_player_percent()`（单一真值，UI 不再折算）。
3. **★ 是我上一轮引入的**：seek 之后 `bytes_fed` 仍从文件头累计、`src_frames_done` 却归零重算，
   "实测平均码率"那段拿这两个一除 ⇒ 时长被估飞 ⇒ 进度条被变化的分母扯着来回飘。
   修法：加 `bytes_base`（开曲=0，每次 seek=当时字节），估算只用差值；
   并且**算准一次就锁**（`dur_locked`，换曲子才解锁）—— 时长不该随位置变。

## ★ 追加（同日第四轮）：「暂停后再播放，进度条从 0 开始」是我上一轮留下的漏网

### 现象
暂停（含被 AI 打断）后再点播放：**声音确实跳回停住的位置**，但屏上的进度条和时间
从 00:00 重新爬。

### 根因（一行顺序问题）
开新曲那段既有代码无条件先 `s_pos_sec = 0; s_dur_sec = 0;`，而我上一轮的恢复逻辑
（`else if (s_pos_pct > 0) apply_seek(s_pos_pct);`）就写在它后面同一个分支里 ——
`apply_seek` 的秒数是 `s_dur_sec * pct / 100` 折算的，`s_dur_sec` 刚被清成 0 ⇒
秒数算出来还是 0 ⇒ `dst_frames_done = s_pos_sec * dst_rate` 也从 0 起算。
字节位置跳对了、秒数没跟上，于是"听着在 1:23、看着从 0:00 爬"。

### 修法
把不变量写清楚：**位置与时长属于"这一首"，不属于"这一次打开"**。

```c
const bool resume_same = (s_pos_idx == req_idx && s_pos_pct > 0);
if (!resume_same) { s_pos_sec = s_pos_pct = s_dur_sec = 0; s_pos_idx = req_idx;
                    bytes_base = 0; dur_locked = 0; }        /* 换歌才重置 */
s_playing = 1; s_cur_idx = req_idx;
if (resume_same) apply_seek(s_pos_pct);                      /* 时长沿用，不重估 */
```

日志尾巴加 `[续播]`，真机一眼能看出走的是哪条分支。

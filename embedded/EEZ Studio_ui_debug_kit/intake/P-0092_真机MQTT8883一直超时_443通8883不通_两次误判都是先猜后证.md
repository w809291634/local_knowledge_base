# P-0092 · 真机 MQTT 8883 一直超时（443 OTA 通、8883 MQTT 不通）—— 两次误判都是「先猜后证」

- **工程**：p4_touch_lcd4_3_exp / lvgl_demo_ai（xiaozhi-esp32 + esp_hosted SDIO + ESP32-P4）
- **日期**：2026-10-03
- **工具**：WorkBuddy
- **状态**：**open**（未根治，已定位到边界，等用户在 A/B/C 三选一里决策）
- **标签**：真机,MQTT,esp-tls,8883,OTA,443,取证,先猜后证,esp_hosted,SDIO,MSS
- **关联提示词**：PR-0113

## 现象（看到什么）

真机串口每 60 秒刷一遍，无尽循环：

```
E (1178740) esp-tls: [sock=54] select() timeout
E (1178740) esp-tls: Failed to open new connection in specified timeout
E (1178750) MQTT: ... ESP_ERR_ESP_TLS_CONNECTION_TIMEOUT
I (1183744) MQTT: Connecting to endpoint api.tenclass.net
```

用户原话：「总是一个错误」。同时贴的完整启动日志里**其它一切正常**：
`Application: Activation done`、`ShowNotification: 版本 9.9.9`、AFE 唤醒词模型加载成功、
`user_io_esp: screen: wake by touch`（UI 活着）。

用户追问：「可以使用吗」。

## 复现（怎么稳定重现）

设备连上 Wi-Fi 后必然复现，与操作无关：`MQTT_RECONNECT_INTERVAL_MS = 60000`
（`xiaozhi-esp32/main/protocols/mqtt_protocol.h:22`）决定每 60s 重试一次，永不放弃。

## 根因（真正的原因）

**未定位到唯一根因，但已把范围压到很小**。决定性事实表：

| 通道 | 端口 | 结果 |
|---|---|---|
| OTA / 激活（HTTPS） | 443 | **通**（`Activation done` 已打） |
| MQTT（TLS） | 8883 | **不通**（`select() timeout`） |

同一设备、同一域名（`api.tenclass.net`）、同一 Wi-Fi、同一时刻。**这条对照是本案全部价值所在**：
它一次性排掉了 Wi-Fi、DNS、路由、电源、天线等一堆公共因素——链路是好的，
只是 8883 这一条出去的包没有回音。

已排除（逐条带证据）：
- **DNS / 建 socket**：`sock=54` 说明 socket 已创建成功，卡在之后。
- **证书**：`CONFIG_MBEDTLS_CERTIFICATE_BUNDLE_DEFAULT_FULL=y` 已开。
- **MTU / SDIO 隧道**：P4 走 esp_hosted，`ESP_TRANSPORT_SDIO_MAX_BUF_SIZE = 1536`；
  TCP MSS 1440 + IP 20 + TCP 20 + 4 = **1484 < 1536**，根本没超。
- **服务器端**：PC 在同一网络实测 443/8883/80 全 OPEN，`openssl s_client` 握手成功，
  HTTP 200 / 2.1s —— 服务器是活的。
- **NVS 分区**：16KB 够用。
- **陈旧 endpoint 假说**：固件 `strings` 查硬编码 MQTT 域名**零命中** →
  endpoint 只可能来自 NVS（`ota.cc:146-164` 是唯一写 `mqtt{}` 段解析的地方），
  而日志明写 `Connecting to endpoint api.tenclass.net` = 当前正确的官方域名。

### ★★ 我犯的两次判断错误（都被用户贴的日志推翻 —— 这才是本案最值钱的部分）

**错误 1：猜「NVS 里存了失效的陈旧 endpoint」**
→ 被 `I (1183744) MQTT: Connecting to endpoint api.tenclass.net` 一行直接推翻：
那是当前正确的官方域名，PC 侧实测也确认可达。

**错误 2：猜 `CONFIG_LWIP_TCP_MSS=1440` 撑爆 SDIO 隧道**
→ 被 `W (24078) Display: ShowNotification: 版本 9.9.9` 一行推翻。
取证链：该串来自 `application.cc:299-308` 的 `HandleActivationDoneEvent()`
（`:300` 打 `Activation done`、`:308` `display->ShowNotification(message.c_str())`），
版本号取自 **`lvgl_demo_ai/CMakeLists.txt:77` 的 `set(PROJECT_VER "9.9.9")`**
（注意不是 `xiaozhi-esp32/CMakeLists.txt:12` 的 2.3.0，那个被顶层覆盖）。
⇒ 说明 **OTA 激活（HTTPS 443，要传整条证书链的大包）已经成功**。
大包都过去了，小包不可能被 MTU 卡住；且算术上文已证 1484 < 1536。
→ **明确结论：不要去动 MSS**（动了只会引入新问题，且掩盖真因）。

**为什么会连错两次（方法论根因）**：两次都是**先猜配置、后找证据**，
而猜的依据是「经验里这类问题通常是……」，不是日志。翻案的两条证据恰恰都是
**用户贴的日志里本来就有的字符串**，只是我一开始没拿它当判据用。
→ 与 P-0068（真机「现象不对」先取证再改码）是同一条铁律的第二次违反。

## 修复（做了什么）

**未修（等用户决策）**。给出的三选一：
- **A**：加诊断日志，把 DNS 解析结果、TCP connect 各阶段耗时打出来，定位丢在哪一步（要烧一次）。
- **B**：摘掉 MQTT 链路（或加编译开关默认关），刷屏立刻消失，本地功能全保留。
- **C**：不管它（60s 刷一次，不影响本地功能）。

另回答了「可以使用吗」：**MQTT 不通 ⇒ 本地功能都能用，云端对话不能用**。
唤醒词（本地）、AFE、ES7210 四通道麦克风、codec、UI 全部初始化成功，设备停在 `待命`；
但唤醒后的音频要经 MQTT 上云做 ASR/LLM/TTS，这一步断了 ⇒ **不会有任何回答**。
（这点的产品含义：设备看起来"活着"但"哑了"，很容易被误判成 UI/音频 bug。）

## 证据（数字 / 命令输出）

- 端口对照：443 通（`Activation done`）、8883 不通（`select() timeout`）。
- 源码定位：`mqtt_protocol.cc:134` `Connecting to endpoint %s`、
  `:136` `int broker_port = 8883;`、`:89-90` 重连定时器；
  `mqtt_protocol.h:22` 60000ms。
- 版本取证：`lvgl_demo_ai/CMakeLists.txt:77` `set(PROJECT_VER "9.9.9")`
  → `application.cc:299-300` `HandleActivationDoneEvent()`。
- `strings <固件> | grep -i mqtt域名` → **零命中**（endpoint 非硬编码）。
- SDIO 余量：1484 < 1536（`ESP_TRANSPORT_SDIO_MAX_BUF_SIZE`）。
- PC 侧对照：443/8883/80 全 OPEN；`openssl s_client` 握手成功；HTTP 200 / 2.1s。

## 沉淀（新增断言 / 案例 / 文档）

- ★★ **「通道对照表」优先于「猜配置」**：遇到"某个网络功能不通"，第一件事是列一张
  **同设备 / 同域名 / 同网络 / 同时间**下哪些端口通、哪些不通。443 通 + 8883 不通
  立刻把嫌疑范围从"整条链路"缩到"这一条出去的包"，Wi-Fi/DNS/路由/电源整批出局。
- ★ **日志里的「无关」字符串常常是最硬的判据**：`ShowNotification: 版本 9.9.9`
  看着是 UI 噪音，却反证了 OTA(443) 大包已成功 → 直接枪毙了 MTU 假说。
  **先通读一遍完整启动日志并逐条归因，再动手猜。**
- ★ **先确认"能用/不能用"的边界再谈修**：本案边界 = 本地全可用 / 云端对话不可用。
  说清边界比给一个没验证的修复更重要（用户第一诉求就是"可以使用吗"）。
- **不要用"改配置"来试探未知根因**（尤其 MSS/超时这类）：改了要么无效、
  要么掩盖真因，还会让下一次取证拿到被污染的数据。
- 同型教训：P-0068（真机先取证再改码）、P-0090（写板级桥接前先 grep 确认符号真身）。

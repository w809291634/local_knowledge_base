# P-0124 · 开机视频段：LVGL 9.4 解内存里的 JPEG 打不开，根因是 FS_MEMFS 没开而不是解码器缺

- **工程**：lvgl_demo_ai / eez-test（ESP32-P4 + LVGL 9.4 + EEZ Studio flow）
- **日期**：2026-10-16
- **工具**：Qoder
- **状态**：fixed（仿真端）/ open（真机端口未接线）
- **标签**：开机视频,MP4,MJPEG,JPEG解码,lv_image,FS_MEMFS,lv_image_decoder,lv_conf生成,仿真上屏,黑屏
- **关联提示词**：PR-0204～PR-0207（见 prompts/PROMPT_LOG.md）

## 现象（看到什么）

仿真走路器 `--walk=bvid` 播 `build/sim_sd/boot.mp4`：解封装、时间轴、统计全部正常
（`err=0 帧 42/60 丢18 解码错0 800x480 fps=20.00`），但截图 `bvid_f25_*.png` **整屏是黑的**，
只有底色遮罩，看不到任何一帧画面。日志里没有任何报错。

## 复现（怎么稳定重现）

```
python design/make_boot_mp4.py            # 生成 800x480@20fps 的 MJPEG-in-MP4 测试片
python design/sim.py --walk=bvid          # 播第 25 帧并截图
```
把帧包成 `lv_image_dsc_t{ header.cf = LV_COLOR_FORMAT_RAW, data = jpeg字节 }` 交给
`lv_image_set_src()` —— 稳定黑屏，且 `lv_image_decoder_get_info()` 这一步是过的
（尺寸正确，所以控件占位、不报 unknown type），只在真正取像素时什么都没有。

## 根因（真正的原因）

**LVGL 9.4 的 tjpgd 解码器，「内存里的 JPEG」这条分支整段被 `#if LV_USE_FS_MEMFS` 包着。**
`src/libs/tjpgd/lv_tjpgd.c:158`（`decoder_open` 里；`get_info` 那条同理，在 :94）：

```c
if(dsc->src_type == LV_IMAGE_SRC_VARIABLE) {
#if LV_USE_FS_MEMFS
    ... lv_fs_make_path_from_buffer(&path, LV_FS_MEMFS_LETTER, img_dsc->data, ...);
#else
    LV_LOG_WARN("LV_USE_FS_MEMFS needs to enabled to decode from data");
#endif
}
if(f == NULL) return LV_RESULT_INVALID;
```

它不直接吃内存指针，而是把这段内存**包成一个假文件**再走 `lv_fs_*`。所以：
1. `LV_USE_FS_MEMFS = 0` ⇒ open 直接 INVALID，`lv_image` 拿不到像素 ⇒ 黑屏，**不报错**（只有一条 LV_LOG_WARN，仿真默认日志级别看不见）。
2. 就算开了，`LV_FS_MEMFS_LETTER` 还必须是**一个真实字母**——默认 `'\0'` 等于驱动不注册，`lv_fs_open` 找不到盘符照样失败。

第二个坑：`lv_image_decoder_dsc_t` 的**完整类型不在公开头**里。
`src/draw/lv_image_decoder.h` 只有前向声明，结构体定义在
`src/draw/lv_image_decoder_private.h`（内核自己的 `lv_draw_image.c` 也是 include 这个 private 头来循环解码的）。
而仿真侧的包含路径是 **lvgl 根目录**（`-isystem <apl_lvgl>`），所以拼路径必须带 `src/` 前缀：
`#include "src/draw/lv_image_decoder_private.h"` 可以，`#include "draw/lv_image_decoder.h"` 报
`No such file or directory`（我先前就是被这条误判成「拿不到，得改 PC_SIM 的 include」）。

第三个坑：解码缓存。`lv_image_decoder_open()` 的 `args.no_cache` 不置 true 时，缓存按**源指针**索引；
每帧传的都是同一个 `&raw`，于是第 0 帧解一次、后面 59 帧全命中缓存 ⇒ 画面冻在第一帧。

## 修复（做了什么）

1. `design/sim.py:write_lvconf()` —— 仿真这份 `lv_conf.h` 是**生成物**（真值源是 `design/lv_conf.h` + 这个函数），
   所以只在生成侧加：强制 `LV_USE_FS_MEMFS 1`，并把 `LV_FS_MEMFS_LETTER` 从 `'\0'` 换成 `'M'`。
   真机那份保持 0（真机端口直写 DPI 帧缓冲，根本不经 LVGL）。
   ★ 不要手改 `design/sim_cmake/lv_conf.h`，下次生成就没了。
2. `src/native/platform/bv_mp4.cpp` 的 PC 端口 `bv_present_frame()`：显式走解码器
   （`lv_image_decoder_open` → `lv_image_decoder_get_area` 逐 MCU 条带搬进自己的整帧缓冲 → `close`），
   再把 RGB888 像素喂 `lv_image`。循环写法照内核 `lv_draw_image.c:img_decode_and_draw()`：
   四个坐标先全填 `LV_COORD_MIN`，`while(res==OK)`，返回 INVALID 那一拍的坐标是上一拍的残留、不能用。
3. `boot_seq_tick()` 里把视频段接在「8/8 自检 + 停留」之后、「切 Main」之前：先 `bvid_probe()`，
   有文件才 `boot_video_play_simple()`，没有就打一行日志跳过 ⇒ 真机（端口未接线）行为不变。

## 沉淀（新增断言 / 案例 / 文档）

- **规矩**：仿真要「解内存里的图片」= `LV_USE_FS_MEMFS` + 一个真盘符，两个都要在 `write_lvconf()` 里给。
  这条是「LVGL 9.x 内存源解码」的通用前提，不止 JPEG（lottie 同理）。
- **别急着改仿真器目录**：报 `No such file or directory` 时先去看目标的 include 列表
  （`build/CMakeFiles/<tgt>.dir/includes_CXX.rsp`），路径前缀写错和真的没挂上，症状一模一样。
- **格式选择**：tjpgd 原生输出就是 RGB888（`dsc->header.cf = RGB888; stride = w*3`），
  仿真端再转 RGB565 只是多一趟全帧遍历；真机要 RGB565 是在**写 fb 那一层**按面板格式转，不在这里。
- 未加 `tools/audit_ui.py` 断言：这是运行期行为，静态审计拦不住。

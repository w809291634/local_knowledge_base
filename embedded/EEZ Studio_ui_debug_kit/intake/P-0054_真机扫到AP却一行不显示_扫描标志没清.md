## 现象（看到什么）

真机串口日志说明扫描**确实拿到了结果**：`disconnect` → `scan done: 14 APs` →
`scan results published to UI slots`，但 UI 里「可用网络」列表**一行 AP 都不显示**，
整块只剩「正在搜索网络…」。用户报的现象原话：「没有ap显示到 UI 中」。

## 复现（怎么稳定重现）

真机进「网络与连接」触发扫描，扫到 AP 后列表区一直不出来（与操作无关，扫完即如此）。
★ PC 仿真**复现不了**：仿真走 `io_pc` 的假状态机，根本没有 `s_scan_in_progress` 这个标志，
门禁（G1-G5 / `all.py --sim`）照不到这条路径 —— 只能真机复现（PR-0105 记录）。

## 根因（真正的原因）

`s_scan_in_progress` 在**扫描成功和失败两条路径都没清**，于是
`io_sample_inputs` 里的

```cpp
state = s_scan_in_progress ? 1 : snap.state;
```

恒为 1 → `wifi_state` 恒 = 1 → UI 列表的 `hiddenExpr="wifi_state == 1"` **永久隐藏**，
只剩「正在搜索网络…」那一块。
**为什么以前没发现**：这个标志是设备侧（`io_esp.cpp`）专有的，PC 仿真的假状态机没有它，
所以流水线全绿也照不到 —— 与 P-0045 / P-0050 记的「设备侧文件是 PC 构建盲区」同一类，
只不过那两条是编译盲区，本条是**运行期状态盲区**。

## 修复（做了什么）

`src/native/platform/io_esp.cpp` 的 `do_scan_locked`：

1. 改成 **`do{ ... }while(0)` + `break` 的单一出口**，成功 / 失败路径都清 `s_scan_in_progress`；
2. 再加 **15s 看门狗**：万一将来又有路径漏清标志，超时也强制回列表态（不再永久卡「搜索中」）。

## 证据（数字 / 命令输出）

- 串口三行连打（`disconnect` → `scan done: 14 APs` → `scan results published to UI slots`）
  ⇒ 数据已发布到 UI 槽位，界面却没显示，把嫌疑压到「显隐条件」而不是「扫描/数据」。
- 判据链：`state = s_scan_in_progress ? 1 : snap.state` → `wifi_state` 恒 1 →
  列表 `hiddenExpr="wifi_state == 1"` 恒为真 = 恒隐藏（MEMORY.md 铁律：hiddenExpr **为真 = 隐藏**）。
- 第一版用 `goto` 做单一出口，C++ 报 **`jump to label crosses initialization`**，
  被 `design/_device_syntax_check.py` 当场抓到 → 改用 `do{}while(0)+break`（PR-0105 的「坑」记的原文）。
- 修复后的真机复验输出：（原始记录未包含，不臆测；`index.md` 本行状态记为 fixed）。

## 沉淀（新增断言 / 案例 / 文档）

- ★ 「进行中」这类状态标志必须有**单一出口**清理，成功 / 失败 / 超时三条路径都要覆盖；
  清不干净就给一个看门狗兜底（本案 15s），别让 UI 永久停在过渡态。
- ★ **C++ 里别用 `goto` 做单一出口**：跨过变量初始化的 jump 直接编译失败；
  用 `do{...}while(0)` + `break`（本案实测）。
- ★ 设备侧专有的状态标志 PC 仿真照不到（`io_pc` 假状态机没有它）：这类问题只能真机取证，
  归入 P-0045 / P-0050 / P-0052 的「设备侧盲区」系列。
- 可加断言（本次未加）：扫 `hiddenExpr` 引用的 native 变量，在设备侧写入点检查是否所有
  置位路径都有对应的复位路径。

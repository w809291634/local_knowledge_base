# 硬件 ⇄ UI 分离架构（生成式 UI + 自写业务代码 + PC 仿真跑同一份代码）

> **适用范围**：任何「UI 由代码生成器产出、业务逻辑自己写、还要在 PC 上仿真同一套逻辑」的
> 嵌入式 LVGL 工程（EEZ Studio / SquareLine / GUI-Guider / 自研 DSL 皆适用）。
> 本文只写**可迁移的部分**：目录、角色、不变式、判据、反模式。具体工程的路径与数值一律不写，
> 实例索引见 §11。
>
> **一句话**：UI 侧只认「变量名 + 动作名」，硬件侧只认端口函数，中间靠**一份契约头**对接；
> **选哪一份平台实现在编译期定死，运行期没有 `if(真机)`**。
>
> 相关：通用方法论 `PLAYBOOK.md`；操作手册 `skills.md` §11.21 / §11.36 / §11.38 / §11.39；
> 单点事故流水 `intake/P-0020`、`P-0041`、`P-0110`、`P-0113`、`P-0115`、`P-0116`、`P-0119`、`P-0124`。

## 0. 文件目录结构（第一步：先认路，再谈机制）

分离做得干净的工程，**目录形状本身就能读出架构**。名字随项目变，**角色不变**——
拿到任何这类工程，先把目录归到这四个角色上，后面所有规则才有落点。

### 0.1 目录树与角色

```
{DESIGN}/                 设计源 —— 人写，唯一真值源
  ├ {页面与控件描述}          DSL 脚本 / GUI 工程文件（只能有一个真值源，别两份并存）
  ├ {生成器胶水}              把描述编译成 ① 的脚本；含"变量表/动作表同步"这类对账逻辑
  ├ {仿真接入}                仿真入口模板 + 仿真侧框架配置（假外设根目录、裁剪开关）
  └ {验收工具}                出图、比稿、静态审计、交互走路脚本
                            ★ 改 UI 只动这里；动 {GEN}/ 等于没改

{GEN}/                    ① 生成层产物 —— 只读
  ├ {界面构建}                控件树 + 事件回调挂载点 + 双向绑定表达式求值
  ├ {动作声明}                extern void action_<name>(...)
  ├ {变量声明}                extern get_var_<name>() / set_var_<name>()
  └ {注册表与入口}            动作函数指针表、变量表、ui_init() / ui_tick()

{NATIVE}/                 ②③ 业务层 —— 人写
  ├ {契约}                    model.h / model.c
  │                           ★ 唯一被 UI 侧与硬件侧同时 include 的头
  │                           输入状态数组 + 输出命令环 + user_init() / user_tick()
  ├ {适配}                    bridge_actions.c / bridge_vars.c
  │                           上面那些 extern 符号的**唯一定义处**；只转发，不存数据
  └ platform/               ④ 平台层 —— 唯一因环境而不同的目录
      ├ io_iface.h            端口契约：全工程唯一"提硬件"的头
      ├ io_sim.c              仿真后端：假数据 + 把命令打印出来（回声即验收）
      ├ io_hw.c               真机后端：驱动、worker 任务、快照发布
      └ io_{subsystem}.c/.h   子系统端口（SD / 网络 / 音频 / 视频…）
                              共享半截 + 平台半截放同一个文件，用预处理分界

{APP_MAIN}/               装配 —— 建 UI 线程的周期任务：ui_init() 一次，
                          每拍 ui_tick() + user_tick()
```

### 0.2 每个目录怎么自证身份

| 目录 | 角色 | 谁产出 | 可写 | 判据（怎么确认它真是这层） |
|---|---|---|---|---|
| `{DESIGN}/` | 设计源 | 人 | ✅ | 改它必须跑一次生成，产物才变 |
| `{GEN}/` | ① 生成层 | 生成器 | ❌ | 文件头常带 `generated / do not edit`；重新生成后你的改动消失 |
| `{NATIVE}/{契约}` | ③ 契约层 | 人 | ✅ | 被 `{GEN}` 与 `platform/` **同时** include |
| `{NATIVE}/{适配}` | ② 适配层 | 人 | ✅ | 里面有 `action_*` / `get_var_*` 的**函数体** |
| `{NATIVE}/platform/` | ④ 平台层 | 人 | ✅ | 只有这里能出现驱动头与平台预处理开关 |
| `{APP_MAIN}/` | 装配 | 人 | ✅ | 只有它同时知道"UI 线程"和"周期任务" |

### 0.3 依赖方向（违反任意一条，架构就塌）

```
        {GEN}/  ──include──▶  {契约头 model.h}  ◀──include──  platform/io_hw.c · io_sim.c
           │                          ▲
           │ 声明 action_*/get_var_*  │ 只有转发
           └──────▶ {适配 bridge_*} ──┘
```

- `{GEN}/` 里**不许**出现驱动头、硬件符号；`{NATIVE}/` 里**不许**碰 `{GEN}/` 的内部结构
  —— 要动控件只有两条路：发布变量，或用生成器明确留出的扩展点（用户事件钩子等）。
- **交汇点只能有一个**：契约头。出现第二个"两边都 include"的头，就是分离开始漏的信号。
- 平台差异只允许出现在 `platform/` 内部（文件级选型，或文件内预处理分半截）。
  业务代码里散落 `#if 真机` = 仿真跑的是另一套逻辑，整个"写一次两边跑"作废。

### 0.4 一条信号在目录之间怎么流（把地图和机制接起来）

```
按下按钮      {GEN}/ 事件回调 → action_x(e)
                 │  （声明在 {GEN}/，定义在 {NATIVE}/{适配}）
                 ▼
投命令        {NATIVE}/{契约}  set_output(id) → 环形队列
                 │
每拍排空      {NATIVE}/{契约}  user_tick() → io_x(v)
                 │  （声明在 platform/io_iface.h）
                 ▼
落地执行      platform/io_sim.c  打印回声      ← PC 仿真
             platform/io_hw.c    调驱动/投任务  ← 真机

反向（硬件→UI）：io_hw.c 采样 → set_input(id,v) → get_var_x() → {GEN}/ 表达式 → 控件
```

**读这套代码的顺序建议**：契约头 → 适配层（看有哪些符号） → `io_iface.h`（看端口面多大）
→ 挑一个后端对照读（`io_sim.c` 短、`io_hw.c` 长，两边函数名一一对应）。

### 0.5 拿到陌生工程，5 分钟认路

1. **找生成层**：grep 文件头的 `generated` / `do not edit`，或看哪个目录的文件时间戳总是同秒批量变化。
2. **找契约头**：对每个头 grep "谁 include 它"，**命中 UI 侧与硬件侧两边的**就是契约；
   命中两个以上这种头 = 依赖已经漏了。
3. **数端口实现份数**：`io_iface.h` 有几个实现文件，就等于支持几个平台。
   少一个后端 = 欠债（要么编译不过，要么那个平台静默空操作）。

## 1. 四条不变式（破坏任何一条，整套架构就开始漏）

| # | 不变式 | 破坏后的症状 |
|---|---|---|
| I-1 | 存在**唯一**被 UI 侧与业务侧同时 `#include` 的契约头；业务代码里不许出现 UI 框架内部符号，UI 侧不许出现硬件头 | 改 UI 牵连改逻辑，仿真/真机各修一遍 |
| I-2 | 平台差异**只在编译期**选定（源文件级或文件内预处理级），运行期零分支 | 业务代码里散落 `#ifdef`，仿真里跑的是另一套逻辑 |
| I-3 | 生成器只产出**声明**，**定义**唯一地写在人工层；两边名字必须逐字符对齐 | 链接期 `undefined reference`，且报错不指向真正漏写的那一侧 |
| I-4 | **命令**与**状态**走不同通道，不许挤在同一个变量里 | UI 显示"已执行"而硬件根本没动（回声假象） |

## 2. 四层结构与归属（§0 那张目录树的抽象版）

```
① 生成层   ← 代码生成器产出，永远只读          （= {GEN}/）
   事件回调挂载点 / 动作声明 / 变量声明 / 两张函数指针表 / ui_init()+ui_tick()
② 适配层   ← 你写的，只做转发，不存数据        （= {NATIVE}/ 的 bridge_*）
   action_<name>() 本体、get_var_/set_var_ 本体
③ 契约层   ← 你写的，唯一被两边 include        （= {NATIVE}/ 的 model.*）
   输入状态数组 + 输出命令环 + 两个生命周期函数（init/tick）+ 值联合体
④ 平台层   ← 你写的，唯一因环境而不同的层      （= {NATIVE}/platform/）
   接口契约头 + N 份后端实现（仿真 / 真机 / 单测桩）
```

| 层 | 谁产出 | 可否手改 | 必须存在的符号 |
|---|---|---|---|
| ① 生成层 | 生成器 | ❌ 重新生成即蒸发 | `action_*` / `get_var_*` / `set_var_*` 的 **extern 声明** + 两张函数指针表 |
| ② 适配层 | 人 | ✅ 每加一个信号就改 | 上述每个符号的**唯一定义** |
| ③ 契约层 | 人 | ✅ | `set_input_i/b/s`、`get_input_i/b/s`、`set_output`、`pop_output`、`user_init`、`user_tick` |
| ④ 平台层 | 人 | ✅ | 接口声明 + **每个后端都要有全部实现** |

★ **接口契约头是"强制不遗漏"的机制**：声明加了，所有后端就必须都有本体，否则**单边链接失败**。
这是免费的架构检查，别用"运行时判空/弱符号"绕过去。

## 3. 三条通道与选型判据

| 通道 | 用在哪 | 路径 | 要声明变量吗 |
|---|---|---|---|
| **A · 动作（命令）** | 按钮点击 = 一次性命令：扫描 / 停止 / 提交 / 翻页 | 事件回调 → `action_x(e)` → `set_output(id)` → tick 排空 → `io_x()` | ❌ 不声明 |
| **B · 输出变量** | 滑块 / 开关 → 需要回写的目标值（亮度、音量、进度） | 控件 → `set_var_x(v)` → `set_output` → 同上 | ✅ native 输出 |
| **C · 输入变量** | 硬件状态回显（时间、电量、连接态） | `io_sample()` → `set_input` → `get_var_x()` → 表达式绑定 | ✅ native 输入 |

**判据**：值恒 1、收到即执行/翻转 → A；会被 UI 显示、且外部改了要推回控件 → B/C。

**A 与 B 汇入同一条输出环**，消费点唯一（`user_tick`）⇒ 不会乱序、不会两处排空。

⚠ **动作通道的函数体应当只有一行投递**（`set_output(id, v)`）。在里面写业务分支、
调硬件、碰 UI 框架，等于把②层变成第二套业务逻辑，仿真与真机的差异就会从这里长出来。

## 4. 变量桥的三条硬规矩

1. **存储只在契约层。** 输入按 `id` 各占一个**独立槽**（整型数组 + 每 id 一个定长字符串缓冲）。
   ★ 禁止按「`id - 某个基准`」算数组偏移 —— 中途插入一批新 id 会让后面全部错位，
   而且症状是"某个 Label 显示成隔壁那条"，极难归因。
2. **`get` 与 `set` 必须落在同一块内存。** 生成器每帧执行「`get` 值 ≠ 控件值 ⇒ 回设控件」，
   读的是另一个槽，就会把用户刚拖动的值打回去 = **单击闪烁 / 滑杆弹回**。
   ★ 这类亚帧竞态 **PC 仿真复现不出来**，只能真机判定（见 `skills.md §11.21`、`intake/P-0110`）。
3. **派生量在 getter 里现算，不要扩接口。** 例如"信号图标"由"连接态 + RSSI"现推，
   硬件侧只如实上报两个原始量 ⇒ 契约面最小、语义单一。
   反向禁令：不要把派生结果回存成第三个输入，那会立刻出现"两个真值源不一致"。

**布尔签名坑**：多数生成器对布尔 native 变量生成 `bool` 签名，人工层若写成 `int32_t` 会链接失败
（或更糟：靠强转蒙过去）。以生成器产出的声明为准，别照抄邻居函数。

## 5. 平台分界机制：怎么选（最容易搞错的一节）

对应 §0 里 `platform/` 目录内部的三种做法，**它们的失效方式完全不同**：

| 机制 | 做法 | 适合 | 失效方式 |
|---|---|---|---|
| ① CMake **白名单** | 构建脚本里列 `if(SIM) 源A else 源B` | 只有 1~2 个整文件级后端 | 新增文件忘进名单 ⇒ **只有一侧编不过**，另一侧静默通过 |
| ② CMake **全收 + 正则排除** | `GLOB_RECURSE` 后 `list(FILTER ... EXCLUDE REGEX)` | 仿真器这种"捞整个目录"的构建 | 排除正则写漏 ⇒ 把真机文件编进 PC（头找不到）；写多 ⇒ 共享文件被排掉 |
| ③ **文件内 `#ifdef`** | 同一 `.cpp` 里 `#if defined(TARGET_HW)` 分半 | 共享逻辑 + 少量平台半截（读文件、起任务） | 无（两侧都编同一个文件，缺半边立刻暴露） |

★ **选择判据**：
- 一个子系统**大部分逻辑两端共用**（解析、状态机、文案表）⇒ 必须用 ③，把共用半截放在预处理之外。
- 一个文件**整份只属于一端**（真机驱动 / 仿真假数据）⇒ 用 ①，但**要同时确认另一端的构建是白名单还是全收**。
- 两端机制**不对称**时（真机走白名单、仿真走全收+排除）⇒ 记住陷阱：
  **新加共享文件只补白名单不够，反过来也只补一边不够**；判据是"两端各自 configure 一次并真的链接过"。

⚠ 别用"运行时函数指针表 + 注册"来做平台选型：它把编译期的"缺实现必炸"降级成运行期的静默空操作，
恰好废掉了 §2 那条免费检查。

## 6. 线程模型配方（硬件状态进 UI 而不卡 UI）

```
主循环（UI 线程）：  lv_timer_handler() → ui_tick() → user_tick()
                     ui_tick   = 生成器：表达式求值、变量推回控件
                     user_tick = 采样入契约层 + 排空输出环投递给 io_*
```

**铁律**：UI 线程只做两件事 —— 读快照、投命令。**零 RPC、零阻塞、零 flash 写、零长循环。**

慢活各起一个 worker 任务，回传用同一套配方：

| 要素 | 做法 | 为什么 |
|---|---|---|
| 优先级 | worker **低于** UI 线程 | 渲染永远优先，慢活抢不过界面 |
| 回传 | 单写者快照 + **代数计数器** | UI 每拍最多推进一代，天然限流 |
| 读锁 | **有界等待**（几毫秒级），拿不到就跳过这一拍 | 无界锁 = 让 UI 为一条数据睡死 |
| 跨线程文本/事件 | **SPSC 无锁环，每拍只取一条** | 加锁或一次排空整队，都会把抖动放大成卡顿 |
| 落盘/擦写类 API | 只在 worker 里调 | 这类调用内部常藏 flash 写，注释里往往不写 |

**唯一可批准的例外**：启动阶段独占整屏、且 UI 上没有任何并发交互时，允许在 UI 线程里阻塞跑一段
动画/视频。这条必须写进注释，并显式声明「不适用于主屏上的任何功能」，否则会被当成先例滥用。

★ 判据（怎么证明没阻塞）：帧率指示器常开 + 对比"启用/禁用该功能"两版的帧周期分布，
不要只看平均值（见 `skills.md §11.33`）。

## 7. 仿真器镜像纪律

**必须镜像**：仿真入口调用的就是真机入口调用的那**同一对生命周期函数**
（`user_init()` 一次 + `user_tick()` 每拍），并且 ①②③ 三层源码与真机**逐字节相同**
（引用工程源码编译，不拷贝、不改写）。

**镜像外设路径的手法**：给"文件类外设"一个可注入根目录（环境变量或配置项），
仿真指向本地假目录、真机指向挂载点，**文件名与相对路径保持一致** ⇒ 同一条代码路径。

**三处不许假装镜像**（在这些地方仿真通过 ≠ 真机通过，必须明写）：
1. **呈现路径**：仿真可能只能走框架控件（如把解码帧贴成一张 image），
   真机是直写显示缓冲、绕开框架。→ 真机的时序/带宽/对齐问题仿真看不到。
2. **时间与性能**：帧率、掉帧数、解码耗时、总线争用，全是设备专属证据。
   ★ 更要防的是**仿真器自己的时钟不跟墙钟**：入口若按固定步长喂框架时钟
   （每圈 `lv_tick_inc(N)` 而一圈真实耗时远大于 N），整段时间轴会被拉伸或压缩，
   于是"看不见动画"这类问题根本查不完（见 `skills.md §11.38`）。
3. **亚帧竞态**：生成器每帧回设控件那类问题（§4 第 2 条）仿真复现不出来。

## 8. 加一个信号的核对清单

| 走哪条 | 要改的地方（缺一处即链接期或运行期出问题） |
|---|---|
| **A 命令** | 设计源加动作 → 重新生成（得到 extern 声明 + 函数指针表项）→ 适配层加 `action_x` 本体 → 契约层加输出 id → 接口头加声明 → **每个后端都加实现** |
| **B 输出变量** | 设计源加 native 变量 → 重新生成 → 适配层 `set_var_x` 投递 + `get_var_x` 回显 → 契约层 id → 接口头 + 各后端 |
| **C 输入变量** | 设计源加 native 变量 → 重新生成 → 适配层 `get_var_x` 透传 + `set_var_x` 空实现 → 契约层 id → 在某处 `set_input_*` 写值 → 界面把属性绑成该变量表达式 |

⚠ 生成器常会"保留工程里多出来的变量"。若如此，删掉的变量会在工程里**复活成声明但无定义**，
症状是链接期 undefined。**以设计源为唯一真值源整体重建**，别做增量合并。

## 9. 反模式清单（每一条都是真实事故）

1. **把命令做成输出变量** → getter 是"最后一次下发的值"的回声，设备执行失败时 UI 仍显示成功。
2. **按 id 偏移索引字符串数组** → 中途加一批 id 后全部错位。
3. **`get`/`set` 不同内存** → 单击闪烁、滑杆弹回；仿真测不出，真机才发现。
4. **靠 CMake 名单分平台，而另一端的构建是 GLOB 全收** → 一侧编得过、另一侧炸，或反过来静默。
5. **在 UI 线程直调慢 RPC / flash 写 / 挂载探测** → 帧率崩、看门狗、堆损坏。
6. **手改生成层**（含"临时加个调试打印"）→ 下次生成静默蒸发，且让回归门禁验的不再是源。
7. **从相邻子系统的配置类推硬件参数**（旋转角、极性、字节序、时钟源）→ 名字像、参考系不是一套；
   这类量**只能烧进去看**，仿真给不出证据（见 `skills.md §11.39`）。
8. **用运行时注册代替编译期选型** → 把"缺实现必炸"降级成"运行期空操作"。
9. **出现第二个"两边都 include"的头** → 依赖方向失控，①层与④层开始互相知道对方。

## 10. 把纪律变成机器检查（自证清单）

- **目录角色对账**：确认"唯一契约头"仍然唯一（对每个头统计被谁 include），生成层目录里没有驱动头。
- **声明/定义对账**：生成层的 `action_*` / `get_var_*` / `set_var_*` 声明集合，与适配层的定义集合
  做 diff，**必须为 0**（双向）。这条断言廉价且能拦住 §8 全部漏写。
- **变量死活审计**：扫"后端写了但 UI 从不读"和"UI 绑了但没人写"两类僵尸变量。
- **绑定控件的变量**：`get`/`set` 指向同一存储的静态检查（或统一走一张表）。
- **仿真时钟**：同一处打框架时钟与宿主真实毫秒，**必须逐点相等**。
- **两端各自 configure + 真链接**：改平台分界后，仿真与真机**都要**完整构建一次；只验一端等于没验。

# 嵌入式问题排查方法论：参考示例入手 / 对比法 / 问题点法 / github 搜索法

> 适用：嵌入式/单片机开发通用（不限芯片与 IDE），也可外推到一般软件调试
> 来源：《问题解决和汇总 v1.2》"问题处理技巧 / 问题解决流程"章节
> 目标：把排查思路固化成可复用的流程，遇到没头绪的问题按此走。

## 结论先行

四种通用打法：① 没头绪 → 从**参考示例**入手；② 有疑似点 → **对比法**（正常/异常对照）；③ 已能复现 → **问题点法**（记录触发→反复触发→修复→再触发验证）；④ 库/工具报错 → **github issues 搜索法**。另外记住一条经验规则：数据显示异常且排除代码错误时，优先怀疑 cache 刷新问题。

## 1. 面对项目没有头绪：从参考示例入手

拿到一个陌生项目/芯片没有思路时，先找官方或厂商的参考示例跑通，再在示例基础上改成自己的需求。示例是"已知能工作"的基准，出问题时随时可以退回基准对照。

## 2. 对比法

找一个**正常的**和一个**不正常的**例子做对照，差异点即嫌疑范围。适合"同一份代码别人能跑我不能跑"、"改了配置后才坏"这类问题——把差异收敛到配置/环境/代码 delta 上。

## 3. 问题点法（复现闭环）

1. 把问题的**触发方式**记录下来；
2. 不断触发这个问题，确认必现路径；
3. 解决它；
4. 按同样的触发方式再操作，**不再出现才算解决**。

价值：把"偶现"变成"必现"，修复有客观验证标准，避免"改了感觉好了"。

## 4. github issues 搜索法

用开源库/工具链报错时，把错误字符串到该仓库 issues 里搜。典型战果：pybind 编译 so 出现 `undefined symbol: __cpu_model`，百度搜不到，github issues 里直接找到解答（cmake 需按 gcc 版本指定参数）。详见 [python/cv-ncnn-pybind-errors.md](../python/cv-ncnn-pybind-errors.md)。

## 5. 数据显示异常的怀疑顺序

LCD 屏幕显示的数据异常、排除代码逻辑错误后，极大可能是 **CPU 操作内存时的 cache 刷新问题**（外设/DMA 改了内存，CPU 读到旧值）。此时查缓冲区是否需要按 DMA/Cache 一致性处理，而不是继续盯显示代码。

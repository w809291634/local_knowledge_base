# 分段线性表查表循环少算一轮：插值参数全 0 → 除零 → 高浓度全部误报 LO（严重）

> 适用：一切"循环内用 arr[i-1] + arr[i] 配对做区间定位"的查表实现，不限本项目
> 来源工程：AppMultiParam（2026-09-30 血糖 22kΩ/17.6kΩ 实测误报 LO，已修复）
> 目标：把「症状长什么样、怎么一步步定位到那一行、为什么杀伤力这么大、同类问题怎么一次性排查干净」讲清。

## 结论先行

**规则：查表函数里 for (i = 0; i < N; i++) 的 N 必须等于表的元素个数；且循环内会访问 arr[i-1] 时，arr[0] 和 arr[N-1] 两个端点必须提前用 if 单独处理（否则 i=0 会访问 arr[-1]）。**

少写一轮的后果**不是"少查一个元素"，而是"输出的插值边界全部保持初值 0"**——调用方拿到 (0,0,0,0) 去做 (Nv2-Nv1)/(Ov2-Ov1) 就是 **0/0**，结果 0，最后被误判成"低于下限"报 LO。编译 0 Error 0 Warning，只有把被测值推到临界点以上才暴露。

## 1. 症状：一条严格的分界线

血糖（GLU）测量出现**分界极其锐利**的失效：

| 试纸电阻 | 温度补偿后 Gt | 现象 |
|---|---|---|
| 22.3 kΩ | 511 | 正常显示 28.3 ✓ |
| **22 kΩ** | **534** | **报 LO** ✗ |
| 17.6 kΩ | 669 | **报 LO** ✗ |

分界线恰好是 **Gt = 530**，对应 **R = 22.19 kΩ**。**所有 R < 22.19 kΩ（≈29.4 mmol/L 以上）的点全部报 LO**，像被一刀切掉。

关键线索：**分界值 530 正好等于参数卡线性表的倒数第二项 BOld[8]** —— 这直接把嫌疑指到"查表区间"上。

## 2. 定位过程（可复用的手法）

教训：**"报错"要带错误码和中间值，否则只能靠猜。**

### 2.1 先把每个错误出口打上码

getGU() 有 4 个出口返回错误，给每个出口加**唯一错误码 + 相关中间值**，通过 BLE 发出：

```c
/*
 * 血糖 LO 定位打印：0x9101 getGU 电流<=0
 *                   0x9102 getGU Gb < floor
 *                   0x9103 getGLUBCL 低于表下限
 *                   0x9104 getGLUBCL 高于表上限
 *                   0x9201/0x9202 温度过低/过高
 * 由 app_config.h 的 DEBUG_LO_PUSH 宏控制，默认 0（发布必须为 0）
 */
#define LO_DBG(code)     Net_Protocol_pushData(code)
#define LO_DBG_V(val)    Net_Protocol_pushData((uint16_t)(val))
```

注意：**本工程没有 BT_Helper_pushData()**（源码里那些调用全是注释、函数未定义），能用的是 **Net_Protocol_pushData()**——数值转十进制字符串从 UART1（蓝牙口）发出。

宏关闭时 LO_DBG/LO_DBG_V 展开为空，参数表达式不求值，**零代码零 RAM 零 BLE 数据**，可安全长期保留。

### 2.2 结果一眼定位

收到的序列末段是 0X3931303230，按 ASCII 解出来是 **"91020"** = **错误码 9102 + 值 0**：

```
Gb = 0  →  Gb < floor  →  return ERROR_METER_GLU_VALUE_LOW  →  屏显 LO
```

**"错误码 + 值为 0" 这个组合是决定性证据**：说明 Gb 被算成了 0，而不是真的偏低。

### 2.3 高频打印会淹没，改用"峰值记录"

getBgmDcCurrent() 在主循环里高频调用，直接 pushData 会被刷屏、也拖慢测量。更稳的做法是**记录峰值、低频输出**：

```c
#if DEBUG_LO_PUSH
volatile uint16_t dbgAdcData  = 0;
volatile uint16_t dbgAdcData1 = 0;
#endif
/* ... 采样后 ... */
#if DEBUG_LO_PUSH
    dbgAdcData  = adcData;
    dbgAdcData1 = (uint16_t)adcData1;
#endif
```

### 2.4 顺带用 ADC 数据反证"不是硬件问题"

把采样值和物理量对起来，可直接排除硬件嫌疑。已知基准 actualDriveVAdcData = 914，则：

```
adcData1 = 2279  →  rfMv = 2279x2000/4096 = 1113 mV
                 →  电流 = 1113x10000/499 ≈ 22.75 uA
                 →  R = 400mV / 22.75uA ≈ 17.6 kΩ
                 →  屏显 37.1 mmol/L
```

几个点的 adcData1 随负载单调变化（1745 / 2279 ...），说明**测量通道本身是好的**——那把问题逼回软件。

## 3. 根因：查表循环少跑一轮

src/Multiparameter.c 的 getGLUBCL()（分段线性校正的"区间定位"函数）：

```c
uint8_t getGLUBCL(uint16_t v, uint16_t *pOv1, uint16_t *pNv1, uint16_t *pOv2, uint16_t *pNv2)
{
    uint8_t ret = 0;

    if (v < BOld[0])      { ret = ERROR_METER_GLU_VALUE_LOW; return ret; }
    else if (v > BOld[9]) { ret = ERROR_METER_GLU_VALUE_HI;  return ret; }

    if (v == BOld[0])          /* 表首：单独处理，防 i-1 = -1 越界 */
    { *pOv1=BOld[0]; *pNv1=BNew[0]; *pOv2=BOld[1]; *pNv2=BNew[1]; }
    else if (v == BOld[9])     /* 表尾：单独处理 */
    { *pOv1=BOld[8]; *pNv1=BNew[8]; *pOv2=BOld[9]; *pNv2=BNew[9]; }
    else
    {
        uint8_t i = 0;
        for (i = 0; i < 9; i++)          /* ← BUG：表有 10 项，只到 i=8 */
        {
            if (v <= BOld[i])
            {
                *pOv1 = BOld[i-1];  *pNv1 = BNew[i-1];
                *pOv2 = BOld[i];    *pNv2 = BNew[i];
                break;
            }
        }
    }
    return ret;
}
```

表有 **10 项**（BOld[0..9]），循环却只到 i<9（最大 i=8），所以：

- 只能命中 [BOld[7], BOld[8]] 及更早的区间，**最后一个区间 [BOld[8], BOld[9]) 永远命中不了**
- v ∈ (530, 740) 时循环一次都不进 if，break 没执行，**4 个输出参数保持调用方给的初值 0**
- 调用方（getGU()）拿到全 0：

```c
volatile float Gb = (((float)Nv2-(float)Nv1)*(Gt-Nv1))/(Ov2-Ov1)+Nv1;
/* = (0-0)*(Gt-0)/(0-0)+0 = 0/0 → 0 */
```

- 回到 getGU() 的下限判定：Gb(0) < floor(5) → **报 LO**

> 端点 v == BOld[9]（=740）因为有单独 if 分支，反而能过——但那是个孤立点，没有实际意义。

## 4. 为什么杀伤力这么大（本质）

普通"少遍历一个元素"只是少处理一条数据；**查表定位函数少一轮，输出的是"未初始化的插值边界"**，而边界会进入**除法**：

```
循环没命中  →  边界全 0  →  分母 0（除零）  →  结果为 0  →  被当成"测量值极小"  →  误报误差
```

**一个数组下标错误，最终表现为一个看起来完全无关的"样本浓度太低"错误。** 这是这类 bug 最难查的原因。

## 5. 修复

```c
for (i = 0; i < 10; i++)     /* 表有 10 项 */
```

同一个文件里的 getGLUTCL()（温度表插值，表有 16 项）有**完全相同的写法**，也少了一轮：

```c
for (i = 0; i < 15; i++)     /* 表有 16 项 */   → 改为 i < 16
```

getGLUTCL() 当时没暴露是因为**参数卡 tV[16] 被整表改成 100（固定 25℃）**，任何温度插值出来都是 100；但一旦把 tV 换回真实温补表，**38~40℃ 区间就会以同样方式除零失效**，所以一并修掉。

## 6. 影响面与验证

| 项 | 结论 |
|---|---|
| 受影响范围 | **血糖专属**。getGLUBCL()/getGLUTCL() 只被 getGU() 调用，getGU() 只被 meterEvtHandle.c 的 GLU 分支调用（各 1 处，grep 确认） |
| TC / TG / UA | 走另一个函数 getG()，**完全不受影响** |
| 修复后 | 22 kΩ → 29.6、17.6 kΩ → 37.1（原来都是 LO）；cap 才真正成为上限 |
| 参数卡侧 | **不需要改卡**。改前无论 cap 设 600 还是 720 都无效——530 以上在代码里是死的 |

**验证顺序**（建议按此执行，避免"改了卡还是不生效"的反复）：
1. 先确认 BLE 打印的**错误码**，确定是哪个出口
2. 再确认**值是不是 0**（值 0 = 查表没命中；值非 0 才是真的越限）
3. 定位到具体函数/行后再改代码
4. 改完用**分界点两侧**各测一个值（如 22.3kΩ 与 22kΩ）确认边界推开

## 7. 同类问题一次性排查方法

这类 bug 的特征是"**循环内用 arr[i-1] 和 arr[i] 配对**"。直接全工程 grep 回溯下标即可：

```
\[i-1\] | \[i+1\] | \[k-1\] | \[idx-1\]
```

本工程结果：**只有 4 处命中，全部落在已修复的两个函数里**（getGLUTCL 2 处、getGLUBCL 2 处），没有第三处。

其余循环逐个确认**不回溯前一个元素**，因此无同类风险（少一轮也只是少处理一个元素，不会产生 0 边界进除法）：

| 位置 | 循环 | 性质 |
|---|---|---|
| argCardEvtHandle.c | i<32 | 遍历 data[33] 查非 0，数量正确 |
| Afe.c x4 | i<32 | **不是数组遍历**：运放建立等待（OPA_REG++; delay; 查 OPA_OUTPUT）|
| I2cMaster.c / i2c.c / Wtn6040.c | i<8 等 | I2C/寄存器位操作 |
| TM1668.c | i<8、seg<7、seg<3 | 数码管段码/位扫描 |
| Iap.c | i<64 | IAP 数据搬运 |
| cache.c | **完全没有 for/while** | 参数加载靠 memcpy |

## 8. 防御性写法（建议长期保留）

即使同类问题已清零，给插值加一层"分母保护"，把"误报 LO"降级为"退化为不校正"：

```c
volatile float Gb = (Ov2 > Ov1)
    ? ((((float)Nv2 - (float)Nv1) * (Gt - Nv1)) / (Ov2 - Ov1) + Nv1)
    : (float)Gt;
```

这样表被写错（相邻值相等）或循环再出边界时，只会 Gb = Gt，不会除零。

## 9. 已确认的其它隐患（同一函数，未改）

- **分式分子用错变量**：调用方写的是 (Gt - Nv1)，严格应为 (Gt - Ov1)（分子分母要同用"原始刻度"做比例）。当前 BOld == BNew（恒等表）时 Nv1 == Ov1，结果不受影响；**一旦把两表改成不同来做真正的线性校正，这里就会算错**。
- **两表必须同步修改**：BOld（原始刻度）与 BNew（线性刻度）配对使用，只改一边会让结果整体偏移，而不是"部分不校正"。
- **两表必须严格递增**：若出现相邻两项相等，(Ov2-Ov1) 为 0，仍然会除零。改表值后务必检查单调性。

## 10. 教训

1. **"值 + 错误码"一起打**，比只打"出错了"强十倍——本次就是靠 9102 + 0 一眼定位的。
2. **看到分界极其锐利的失效，先去对"分界值"**：它往往等于某张表的某个元素值（本次 = BOld[8]）。
3. **纯软件逻辑问题，先用硬件数据排除硬件**：adcData1 随负载单调变化，证明通道正常，省掉一轮硬件排查。
4. **改参数卡之前先确认代码这条路是通的**：本次 cap 从 600 改到 720 毫无效果，因为 530 以上在代码里根本走不到。
5. **"数组少一轮"在查表函数里 = 除零 = 误报**，不是"少一个元素"。凡循环内有 [i-1]，都要把端点单独处理。

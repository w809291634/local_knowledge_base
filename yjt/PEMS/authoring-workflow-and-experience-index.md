# 模板化文档族编写流程与经验索引（AI 工具无关的开工手册）

> 适用：任何由 AI 或人执行的「按公司既定模板批量产出/迭代 Word 文档族」任务（注册资料、技术要求、说明书、验证/确认记录等）。
> 来源：2026-11-09 由多项目交付复盘整理；本文件只做**流程编排与经验索引**，判据细则在各专题文件与 `pitfalls.md` 里
> （为什么要单独有一份编排文件，见 `pitfalls.md` §84）。

## 开工先看：格式速查

**用户特别重视格式，格式必须独立验收。先读本表，再按 §1.3、S2～S10 执行。**
下列字号是常用配置示例，须在 S2 按各份模板及已确认修正确定，不能自动覆盖专门基线；未设的标题层级不额外增加。

| 项目 | 格式要点 |
|---|---|
| 字体字号 | 中文宋体、西文及数字 Times New Roman；正文常用 12pt，表格／图题常用 10.5pt。 |
| 标题封面 | 三级标题常用 16／14／12pt、加粗；封面标题字号、位置和信息表按对应基线。 |
| 段落 | 首行缩进、行距、段前段后距及对齐按本轮确认基线；新增正文与同类段落一致。**缩进只加正文自然段**——标题、图题/表题、目录条目、封面区、表内、文本框、真列表、居中/右对齐段一律不加；写法见 `pitfalls.md` §90，适用范围与保护区边界见 §95，写完必须过 Word 保存再回读。 |
| 编号 | 核对实际显示与连续性，不出现“3.1 3.1”等手写＋自动双编号。 |
| 表格 | 表头、列宽、边框、底纹、跨页及合理合并符合基线；独立记录的编号／名称／结果不得被合并覆盖。**表格必须是正文级 `w:tbl`**：落在 VML 浮动文本框里的表不占正文高度，一改段距就会与正文互相压字，判据见 `pitfalls.md` §96。 |
| 分页分节 | 封面恰好一页；节数、页边距、横竖页按对应基线；无异常空白、大片占位留白或图表裁切。 |
| 目录 | 域目录刷新，已确认的静态目录逐条核对；标题与实测页码一致；按基线无目录者不新增。 |
| 页眉页脚 | 文控编号、模板版号、位置及首页设置符合基线；页码、总页数及起算方式正确。 |

**S7 修复 → S8 独立格式门禁 → S9 最终全页复核。必要项失败或未执行，不得标记格式验收完成；可如实归档工作稿并继续独立工作。**
本表仅汇总现有规则，不替代逐份格式档案；字体细则见 `yjt/PEMS/reference-document-format-and-diagram-requirements.md` 「分类规则 -- 字体与版式」，验收清单见 `yjt/PEMS/dod-checklist.md`。

## 0. 为什么别的 AI 会写坏

同一套模板，出错几乎都落在这十类，本文件的每个阶段都对着它们设了卡点：

1. 把上一个项目/上一版产品的口径当事实照抄（型号、主体、参数、结论、人员名单）。
2. 拿推断值或常识补空白（元器件型号、阈值、日期、测试结果），事后无人能追溯。
3. 只跑闸门不看渲染；闸门全绿≠文档没错（`pitfalls.md` §68）。
4. 新写或移植的判据没做反向测试，判据其实一直在静默放行。
5. 按段落索引批量删元素、按格序往表格里写值，静默吃别的内容与标签（§69、§82）。
6. 按文字找锚点先命中目录条目；改静态目录页码改了整段（§79、§33）。
7. 版式收口排在 Word 刷新目录之前，或收口后不重算交付清单哈希（§36）。
8. 把过程话术（待确认/自动生成/占位/内部注释）写进正文（`one-pass-quality-gate.md` §5）。
9. 上下文被压缩或续接后，直接引用记忆里的旧数字、旧文件状态汇报。
10. 改完就报"已完成"，没有可复现命令与实测输出。

### 1.2 交给其他 AI 执行时的两条规矩

1. 一次只推进一个阶段，阶段结束时必须回显该阶段的完成判据实测值（数字 + 命令），不许跨阶段连着报"都好了"。
2. 换一个 AI 或新会话接手，先读本文件与项目侧的阶段状态文件，再干活；不靠会话记忆里的结论。严格格式动作及实际证据按 §1.3 执行，阶段可连续推进，不要求逐阶段获得用户批准。

### 1.3 严格格式执行与阶段证据（2026-11-10 用户明确要求）

格式是每阶段的完成条件，必须严格按本轮明确的格式要求、对应模板版号和已确认修正执行。正文增加允许自然重排，但不能借“内容已替换”绕过格式继承，也不能以模板原有缺陷为理由忽略已确认的修正要求。

**格式前置：S2～S6 同样严格执行格式基线，不能累计到 S7 才处理。** S2 先定逐份基线，S3 核对骨架后再按其批量生成；S4～S6 写入、扩表和插图时同步应用基线，及时回读并检查结构性变化影响的页面。发现格式错误先修复当前对象，再继续依赖它的批量操作；无法核验时如实记录未执行，继续不依赖该项的独立工作。已有明确基线和授权直接复用。

S7 负责目录刷新后的必要版式收口、自然重排复核与页码同步，不是首次检查格式；最终仍须通过 S8 独立格式门禁和 S9 全页复核。

| 阶段 | 必须完成的格式动作 | 项目工作目录中应有的证据 |
|---|---|---|
| S2 | 逐份确定模板／参照格式与已确认修正，冻结格式基线 | 在已有格式档案或项目配置记录模板哈希、分节及逐节尺寸／页边距、封面、眉脚／首页不同、目录、标题／编号、表格列宽／合并／跨页、图示定位及字体／行距 |
| S3 | 逐项对照骨架，分清应保留结构与已知缺陷 | 结构比对；新增／删除／改写和结构变化的具体位置、依据与影响，不以标题顺序一致代替全部结构检查 |
| S4 | 写入前核对段落属性、编号机制和表格物理单元格 | 槽位映射；表格标签／值格／合并关系；新增行继承检查；独立编号与名称写后回读 |
| S5/S6 | 图片、图题、章节对应，写入后基线不被无关修改破坏 | 图示来源与定位核对；生成后结构差异及封面／表格／编号回读 |
| S7 | 按本项目实测通道刷新目录、收口版式、渲染并同步页码，再渲染 | 具体修复动作、修前修后结果、最终渲染及目录条目—正文标题—实测页码核对；避免破坏分节和首页设置 |
| S8 | 对实际交付物执行格式和对象检查 | 格式／对象模型／渲染报告，覆盖双编号、表格合并覆盖、字号与间距、留白、页眉页脚、图文定位和目录页码；记录检查器未覆盖的维度 |
| S9 | 最终文件每页复核，每份 Word 只读打开；修改后重查受影响范围并完成最终全页核验 | 每份文档的最终 DOCX 哈希、渲染文件哈希、引擎、页数，以及页级结论、问题与修复后复核；截图可只保留问题及复核页，不能只检查截图页 |
| S10 | 仅在适用检查均完成后形成格式验收结论 | 阶段汇总及未决项，最终文件／报告哈希同代；任一必要项失败或未执行，整体保留未完成状态 |

这些证据复用项目已有配置、报告、阶段状态和生成记录，不要求额外复制一套台账。各项分别记“通过／失败／未执行／不适用（有理由）”，无检查结果不能推定通过；同阶段或后续不依赖失败项的工作可继续，但依赖该项的验收不得标记完成。阶段连续推进不等于要求用户逐阶段批准。

“未渲染”“只抽检”“没有刷新目录”“工具暂不可用”必须反映到相应阶段和整体状态；可如实交付工作稿，不得改写为“全部 PASS／全部完成”。来源优先级不替代版式基线，编写完成、格式验收、产品试验和受控批准分别判断。

## 2. 十条铁律（违反即返工，不分项目）

1. **事实只进主事实文件**（`facts.yaml` / `facts.json` / 受控 `config.json` 三选一），脚本、正文、经验库不得另写一套。
2. **格式靠继承**：以基线 `.docx` 就地替换，禁止从零拼文档。
3. **模板只读，输出去新版本目录**，永不覆盖模板、源文档与历史版本。
4. **模板版号是独立一条轴**：新旧版建档与判据互不通用（`iteration-and-versioning.md` §7）。
5. **无证据不填实值**：签署人、测试人员、测试结果、日期、结论，未经注册人/受控记录不得代填。
6. **不编数据**：来源缺失就留白并进待办，不从相近项目、案例或常识推断。
7. **判据必须能失败**：跑不起来、缺依赖、拿不到中间产物一律非零退出，不许降级为弱判据后报通过（§58）。
8. **新判据必做反向测试**：投一个已知坏样本必须命中并让流程失败；对已知好产物不得误报。两者缺一，判据就不算生效。
9. **修改走同源原语**（`tools/docx_ops.py`、`tools/para_ops.py`、`tools/release_ops.py`）：调哪一条见 §10 对照表；
   库里没有的六类（§10.1）才在项目里写，且两个项目重复写过的要提进库里。
10. **汇报只讲可复现证据**：命令 + 实测数字 + 产物路径，没跑过的数字不写。

## 3. 阶段流水线

**阶段不是单向的**：S8 与 S9 要跑成一圈（闸门 → 注入自测 → 修判据 → 复跑闸门），**最后一圈全绿才算数**；
本轮新增或改动过判据、或沿用上一项目的脚本时，先做 S9 的注入自测再进 S8（`pitfalls.md` §83 的四处口径逐项重定）。

### S0 立项与资料冻结
- **格式执行依据**：按照本文件 §6 的六项资料清单格式整理本步骤资料，登记位置与状态，源资料保持只读。
- 动作：先按 §6 展示六项资料清单；核实项目编号、项目名称和可读取的产品说明书三项必填，盘点已提供的技术要求、源码、补充注意事项及 BOM/图纸、历史版本、模板与版号。技术要求、源码和补充注意事项为可选，不要求收齐后才开工。
- 完成判据：三项必填齐全且可用；六项状态和来源已登记，可选缺项注明“未提供”，实际证据缺口记入项目待办。必填缺失时可继续盘点与模板准备，补齐后开始项目正文编写。
- 该读：`one-pass-quality-gate.md` §0~§1、`generality-boundaries-and-precedence.md` §一~§三。
- 停手条件：只有口头描述、没有受控来源的关键字段 → 先问，不生成正式结论。

### S1 事实基线台账
- **格式执行依据**：按照本阶段“值／来源／状态／确认日期／责任人”的台账格式及 `yjt/PEMS/consistency-gate.md` 的来源对照要求，完成本步骤事实登记。
- 动作：逐字段写「值 / 来源 / 状态 / 确认日期 / 责任人」；参考资料按“补充注意事项 > 技术要求 > 程序源码 > 产品说明书”采用，保留冲突原值及采用依据，先更新主事实文件，再同步文档。
- 完成判据：主事实文件通过 Schema 校验；每个正文出现的数字都能反查到一个来源键。
- 该读：`consistency-gate.md`、`pitfalls.md` §72（对账表每个 ✅ 可脚本反查）、§70（留空改实值引出的三类缺陷）。
- 停手条件：同级资料矛盾、适用型号／版本不明或优先级仍不能确定的字段 → 报冲突等裁决，只暂停相关字段；已有优先级可以明确处理的差异直接登记采用依据，不重复要求确认。
- 主体与地址类字段只按模板字段名填（制造商 / 生产地址等），模板没有的关系说明（母子公司、委托生产、资质归属）不写进正文，形态信息留在事实文件与生成记录里（`pitfalls.md` §83）。

### S2 模板基线与版号
- **格式执行依据**：按照 `yjt/PEMS/reference-format-profile-template.md` 的格式档案结构及 `yjt/PEMS/template-baselines.md` 对应版本的基线要求，完成本步骤逐份格式登记。
- **默认模板版本**：注册文档族不特别指定时按此取 ——
  RD-026 / 028 / 029 / 030 / 032 / 052 用 **2.1**，RD-068 / 069 用 **1.0**；RD-057 的模板版号是 **3.0**，但**不进交付族**（见下条）。
  逐份真值以 `template-baselines.md` 版号总表为准，基线件在 `templates/<版号>/`；项目配置里必须显式写 `template_version`，不靠脚本默认推断。
- **交付族成员 = 8 份，不含 RD-057**（注册人 2026-11-10 定：RD-057 已另行规定，不由我们生成）。
  - 交付族固定为：026 / 028 / 029 / 030 / 032 / 052 / 068 / 069。
  - 模板库仍是 **9 份**（含 `templates/3.0/RD-057_可用性报告_3.0_基线.docx`），两者不矛盾：模板库是素材全集，交付族是本次报送清单。
  - 实操三条：① `TPL / NAMES / BUILDERS` 与闸门、verify、manifest 的族清单**只留一处定义**，出处写「族成员 8 份」而不是散落的 `== 8`；② 闸门判据写「交付集合 == 族清单」，不写死数字；③ manifest 与生成记录各留一行「族成员：应有 8 / 实有 N / 不含 RD-057（注册人 2026-11-10 定）」，防止下一轮被当漏项补回来。
- 动作：确认每份文档用哪个版号；核对基线件哈希与档案；登记“模板自带的已知缺陷清单”；按 §1.3 在已有格式档案／配置冻结每份文档的严格格式基线。
- 完成判据：版号总表逐份有值；模板缺陷分成「生成时修 / 原样保留 / 需注册人裁决」三类。
- 该读：`template-baselines.md`、`template-format-audit-2026-10.md`、`templates/<版号>/<件名>_基线.md`、`iteration-and-versioning.md` §7。
- 停手条件：新版模板相对旧版增删章节，而要求是"照旧骨架补回来" → 停，先说明差异。

### S3 结构核查（先结构后内容）
- **格式执行依据**：按照 S2 已确认的逐份格式基线及 `yjt/PEMS/reference-document-format-and-diagram-requirements.md`，核对本步骤的封面、目录、分节、眉脚、编号、表格和图示骨架。
- 动作：比对标题序列、目录形态、分节、表格骨架、图示位置与基线件是否一致。
- 完成判据：**标题序列顺序保持**（`ops.check_heading_text_against_template(模板, 产物)` 的 `order_preserved` 必须为 True），
  而 `template_only` / `output_only` 的差异**不要求为空**——标题随产品内容改写是常态（成熟件实测每份都有非零差异），
  但每一条差异都必须逐条登记为「改写 / 删除 / 新增」并进生成记录或基线变更清单；逐节页尺寸、方向和页边距符合对应已确认基线，节数、首页不同与眉脚关系保留；必要结构变化逐项登记依据与影响；
  按已确认基线确定目录类型，不能因工具未检出域就改判“不适用”。域目录要求 `toc_diagnose` 的 `healthy==True`（含 TOC 指令、begin/separate、域配平），且无 `text_has_toc` 裸指令，随后核对渲染结果；经本轮确认采用静态目录时按确认形式逐条核对标题、导航要求和实测页码；按模板设计不设目录的文档登记不适用，不为通过判据擅加目录；
  页眉页脚版号在本档内唯一且等于本项目模板版号（首页眉/偶数眉/页脚各查一次，并与基线件对比，`pitfalls.md` §85）。
- 该读：`reference-document-format-and-diagram-requirements.md` 各分类节（封面／目录／页面设置／分页）、`docx-fields-and-toc-repair.md` §5/§9、`pitfalls.md` §79、§53、§65。
- 停手条件：未经本轮确认的章节／分节／页边距／眉脚变化 → 回 S2 核实依据；渲染失败时先排查通道，不得直接删除分节或改变首页设置以换取导出成功。已有明确授权的调整按依据执行并留痕。

### S4 槽位清单与生成器

### S7 收口（版式 / 分页 / 目录）
- **格式执行依据**：按照本轮已确认格式基线及下列“该读”中的字体、分页和目录修复细则，完成本步骤收口；分页键按本阶段分类处理，目录页码按最终渲染核对。

  导出 PDF → 按实测页同步目录页码 → 再导出 → 再回收一次实例。
  这条顺序要先按本项目实测确认（哪几份有目录域、哪几份是静态目录），不照抄别项目脚本（`pitfalls.md` §83）；
  收口之后必须重算交付清单哈希，否则清单记的是改前的产物（§36）。
- 完成判据：`tools/docx_ops.py:pagination_audit(doc, cover_texts=[...])` 的返回键要**分三类处置**，不得笼统要求"全部为空"：
  - **缺陷键，必须为空**：`hard_page_breaks`、`stacked_breaks`、`keep_on_body`、`chapter_pad`、`outline_anomaly`；
  - **形态位，只记录不阻断**：`toc_field`（True 只说明本文有 TOC 域，健康与否由 `toc_diagnose` 判）；
  - **必须先分诊再定**：`redundant_breaks`、`numbered_not_in_tree`、`body_page_break` —— 成熟件实测会命中，不能仅凭键非空阻断：
    `redundant_breaks` 表示换页分节符与段前分页同时存在；同源原语注明它不必然多出一页，须结合对应基线与渲染判断。确认造成空白／错页时只修多余控制；无实际缺陷且符合基线时可保留，并登记位置与渲染依据，不能为清零删分节；
    静态目录条目未满足本轮已确认的导航或页码同步要求时，逐项修复（可按实际需要补 TOC 样式、超链接或改走域）；已有明确依据保留静态形式时按 S3 核验，不因“没有 TOC 域／样式”自动重建，
    以及"目录"这类大标题段没有大纲级却带段前分页（改法是给它大纲级，或登记进与生成器同源的豁免表，§49）；
    命中项必须逐项判定为需修复或有依据保留，列出位置、适用依据和核验结果；同类项允许引用同一条已确认规则，但各位置和结果仍须核对，不得整键忽略或未经核验批量填写“模板原样／按注册人口径”。
  字体分区且正文小标题不挂标题样式；编号字形统一；封面独立成页且无空白页；目录页码与渲染实测一致，且页码同步只跑一遍。
- 该读：`reference-document-format-and-diagram-requirements.md` 「分类规则 -- 字体与版式」§6~§10、「分类规则 -- 分页」（空白页五步）、
  `docx-fields-and-toc-repair.md` §6、`pitfalls.md` §36、§38~§42、§45~§49、§54~§59、§66、§83、§86（判据键数与键义以原语为准，别照抄"七项/九项"这种旧口径）。
- 停手条件：压页需要偏离正文基线的行距/缩进 → 不压，记为提示项交人工（§37）；无头实例反复起不来 → 换通道并记进档案（§44、§50）。

## 6. 给任意 AI 的开工六项资料清单与任务提示词

### 6.1 六项资料清单（2026-11-10 用户确认）

每次新建、改版或接续编写的开工回复都展示下表；已有会话值和已核实资料直接填入，不重复索取，不把清单当作需要再次批准的确认单。

| 资料 | 必填性 | 当前值／位置和状态 |
|---|---|---|
| 项目编号 | 必填 | 用户给定或明确项目资料中核实的编号；不得以型号、软件版本或目录数字代替。 |
| 项目名称 | 必填 | 本次文档对应的项目名称。 |
| 产品说明书 | 必填 | 可读取的文件或完整内容引用；如已提供，记录版本和日期。 |
| 技术要求 | 可选 | 已提供的文件／内容引用，或“未提供”。 |
| 程序源码 | 可选 | 已提供的工程目录／附件，或“未提供”。 |
| 补充注意事项 | 可选 | 用户给定的特殊要求、来源优先级、禁用内容或其文件，或“未提供”。 |

状态区分已提供、未提供、不可读取和冲突。必填项缺失、不可读取或冲突时，一次询问缺失的必填项；期间继续资料盘点和模板检查。三项必填齐全就推进正文编写。可选项未提供不阻断编写、不逐项追问，也不用常识补造其内容。

**参考资料采用顺序：补充注意事项 > 技术要求 > 程序源码 > 产品说明书**（2026-11-10 用户确认）。同一适用范围内有明确冲突时采用高优先级内容；高优先级未提供或未涉及该字段时顺次使用下一项。顺序不改变各项必填性，采用结果先回写主事实文件并保留冲突原值和依据。要求口径不等于已实现或已实测通过，适用边界见 `yjt/PEMS/generality-boundaries-and-precedence.md` §一.1。

缺失资料的证据边界：

- 无技术要求：可按说明书等现有来源编写，但不能声称已核对独立技术要求。
- 无源码：可依据说明书推导需求和设计，注明真实来源与未核查实现的范围，不能声称已核查代码实现或发布构建。
- 无补充注意事项：仍须读取说明书已有的安全信息、警示和禁忌，不解释为产品没有注意事项。
- 无有效原始试验／签署记录：不填写实测结果、通过结论、人员、日期或签署；相应记录栏留空，缺口记在项目工作目录。此项是结果证据要求，不追加为开工必填资料。

## 8. 机器环境占位符（B 类路径必须先问用户）

以下每台电脑不同，库里只写做法不写真值，禁止照抄或扫盘猜：

- 模板与基线件根目录、经验库根目录；
- PC 仿真/渲染通道（LibreOffice 可执行文件与独立用户配置目录、Word 版本与通道）；
- Python 环境与依赖来源；
- 配图字体在系统里的实际文件名。

命中占位符时先向用户取真值，写入项目侧配置，不回填经验正文。

## 9. 一票否决清单

覆盖模板或历史版本；把上一项目事实写进通用经验库；无证据填实值或写"通过"；正文出现过程话术；
判据降级为提醒；未做反向测试就宣布新门禁生效；只改 docx 不看渲染；跳过人工目检直接送检；
强制结束用户正在使用的 Word/WPS/LibreOffice 实例。

### 10.1 库里没有原语、必须项目侧实现的六类

同标签多点位取值一致、型号集合或"无型号串"判据、结果列留空/白名单（含豁免列必须填齐；表头行要先探测，表头可能不在第 0 行，列名从表头解析而非写死列号，`pitfalls.md` §71）、
必备图示清单核对、页数核账（取渲染产物或 Word 统计，非 docx 自数）、槽位命中数统计。

这六类要在项目里写成可复现判据并做反向测试；同一功能两个项目各写一套时，把多数派版本提进
`tools/` 或写进本表，避免下一轮又自写第三套（§57、§83）。

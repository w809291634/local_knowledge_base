# 迭代与版本管理：让「反复改」不失控（通用）

> 适用：会经过「评审 → 修改 → 再审 → 再改」多轮的文档族。

## 结论先行

把工作分成两层：**数据层（唯一可改）** 与 **产物层（按轮次只读归档）**。

```
project/
  config.json            # ★ 唯一数据源：型号、功能、指标、编号、厂商、文件清单
  tools/docx_ops.py      # 通用原语库（跨文档、跨项目复用；不含项目数据）
  tools/build_docs.py    # 通用生成入口：读 config + 模板 → 出产物
  tools/consistency_check.py
  templates/             # 参考文档（只读）
  out_V1/  out_V2/       # 历史产物（只读保留，不覆盖）
```

**迭代流程**：改 `config.json` → 重跑 `build_docs.py` → 跑一致性校验 → 渲染对拍。
**绝不逐份手改 Word**——手改无法回退、无法保证多份同步、下轮生成即被覆盖。

## 1. 为什么必须这样

| 手改 Word 的后果 | 数据层生成的好处 |
|---|---|
| 改了 1 份，其余 N-1 份不同步 | 一次改，全量重生成 |
| 无法回退到上一版 | 数据层留快照即可复现 |
| 每轮迭代重新手工劳动 | 下一轮只改数据 |
| 格式被误改、封面错乱 | 版式由模板锁定 |
| 冲突无人发现 | 对账脚本自动查 |

## 2. 版本节奏

| 版本 | 触发 | 备注 |
|---|---|---|
| V1 | 首次成稿 | 首次建立版本记录 |
| V(n+1) | 每次修复问题、纠错、格式/内容调整或需求变更 | 从现场最大轮次递增，不按改动类别固定版本号；详见第10节 |

- 文件名带版次：`<文档名>_V{n}.docx`。
- **旧版本保留**，新版本写**新目录**；永不覆盖源文档与历史版本。

## 3. 每轮迭代留三样

1. **数据层快照**：`config.json` 入库（或另存 `config_V{n}.json`）→ 任意版本可复现。
2. **变更记录**：本版独立修改记录，字段与验收按第10节；Git提交只能作为辅助证据，不替代每版记录。文档内受控修订表按实际业务版本与有效证据更新，不将交付轮次写入模板版号或软件版本。
3. **差异清单**：本轮改了哪些**跨文档数据点**（型号体系、主控、指标阈值），因为这类改动
   会影响所有引用它的文档。

## 4. 提交信息格式（本知识库统一）

```
<工程名>：<更新类别>：<更新描述>
```

- 中文；更新类别：`doc / code / fix / other`。
- 示例：`PEMS：doc：V3 封面独立成页并补充过简章节，型号表统一为30型号`

## 5. 最容易失控的三处

| 失控点 | 现象 | 防法 |
|---|---|---|
| 基线漂移 | 同一集合在不同文档来回横跳 | 基线写死在 config，只改一处 |
| 手改产物 | 有人直接改 docx，下轮被覆盖 | 产物目录视为只读；改动一律回数据层 |
| 引擎与内容耦合 | 改版式要动内容映射 | 编排只描述「内容」，版式由模板决定 |

## 6. 回退

- **产物层**：保留所有历史目录，基于选定历史内容生成新的下一版本；记录回退来源和原因，不删除旧目录或复用旧轮次。
- **数据层**：通过新的受控变更恢复选定历史数据，保留本轮与历史快照，不用恢复操作覆盖历史产物。
- **模板层**：参考文档只读，不被修改，可随时重跑。

## 7. 模板版号是独立的一条轴

模板自身有版号（写在页眉，如 `QR/RD/026   2.1`；RD-026 自 2026-11-20 起默认 2.1_v3），与产物目录的 `*_V{n}/` 是两条轴，不得混用同一个"版本"字样。

- 模板改版时：旧版基线件与判据档案原样保留，新版单独建档；配置里显式写 `template_version`，生成器与闸门只取该版判据。
- 两版产物不混在同一版本目录，也不得用新版"无目录/无章节"判据去检旧版稿，反之亦然。
- **版式冲突的优先级**见 `reference-document-format-and-diagram-requirements.md` 头部「格式要求的优先级裁决」（注册人点名的模板版号基线 > 通用规则；模板自身不一致按原样，统一须先确认并写进版本说明）；本文件不重复登记格式条文。
- 落位约定：`template-baseline-<文档编号>-<版号>.md` + `templates/<版号>/<基线件>`；差异表只写在**新版**档案里，旧版档案不重复。


## 8. 版本目录、文件名与交付包的构成（唯一写法）

| 对象 | 写法 | 说明 |
|---|---|---|
| 输出目录 | `<族名>_V{n}`（如 `PEMS-嵌入式_V7`） | 只有族名与轮次。模板版号、交付主体、型号、工具名一律不进目录名 |
| 产物文件名 | `<文档编号> <文档名>_V{n}.docx` | 后缀 `_V{n}.docx` 由同一个 `VER` 派生，与目录名严格同号 |
| 交付包 | `<项目号>_<产品名>_<族名>_V{n}.zip` | 需要标主体/型号时写在这里，不写进目录名与文件名 |
| 草稿与外部工具产物 | `<族名>_V{n}_{来源标记}`（`_codex`、`_manual` 等） | 独立目录；不进受控交付目录，不作为基线继承，不作为闸门对象 |

三套版本号各归各处，不得互相顶名：

| 轴 | 取值处 | 落点 |
|---|---|---|
| 模板版号 | 页眉原值、配置 `template_version`（逐文档一张表） | 决定用哪套结构判据 |
| 文档族轮次 | 目录名与文件后缀 `V{n}`、`manifest.doc_round` | 决定交付与回退；**只落这三处与生成记录／版本说明，不进文档正文** |
| 软件发布/完整版本 | 正文与封面里的 `V…`、`manifest.software_version` | 申报口径，与上两轴无关 |

**软件发布版本写法（注册人 2026-11-17 定）：嵌入式 PEMS 的发布版本只写 `V1`，不写 `E V1`，正文也不体现移动端版本。**
- 字母含义：**`E` = 嵌入式、`M` = 移动端**，二者都是内部软件标识，不是注册口径。
- 依据：送检要求「软件发布版本号：V1」；注册口径只认 `V1`，带字母前缀会被判成写法不一致。
- 落点：052 §1.1 软件版本、052 §4.4.2 软件发布版本、052 §4.4.3 命名规则示例、032 §1.2 软件系统句、030 软件版本描述章。
  **不落点**：029 第九章「软件异常报告表」与「软件异常解决测试记录表」的「软件版本」格——该两表是送检时填实测记录的空白表单，整表不预填（注册人 2026-11-23 定）。
- 同一产品族若同时交付移动端文档，移动端版本（`M …`）只在**移动端自己的文件族**里写，不写进嵌入式族。


**反例（都是历史上真出现过的形态）：** 把模板版号或主体拼进轮次串 —— `<族名>_模板<版号>_V{n}_<主体>`、
`<族名>_<主体>_V{n}`、`<族名>文档V{n}`。后果是换模板版号时轮次断裂、文件名后缀与目录不同号、
每轮都要重写哈希基线与页码同步判据。已存在旧形态时不强行改名，
在项目侧写一张「旧形态 → 新形态」对照表，新轮次起按本节执行。

## 9. 默认版本号怎么算（禁止硬编码字符串）

1. **单点定义**：项目侧只允许一处定义 `VER / OUT / SUFFIX`（`work/version.py` 或等价配置）。
   同一项目出现第二处默认值（哪怕只是另一份生成器脚本自带一份），即为缺陷，先合流再生成。
2. **默认值 = 现场推导**：扫描项目根既有 `<族名>_V*` 目录，取最大 n，默认 `V(n+1)`；
   显式环境变量（如 `PEMS_VER`）才允许覆盖。写死字符串会让默认值落后若干轮，一跑就重刷旧目录。
3. **推导过程要打印**：生成前打印「已存在轮次 / 本轮默认轮次 / 是否被环境变量覆盖」，让人能当场拦住。
4. **已存在即拒写**：目标目录存在时拒绝写入，重新推导并采用下一版本；禁止用`--force`、改名备份或“同版重建”复用旧轮次。用户2026-11-24明确要求的每次修复/变更递增与记录规则见第10节。
5. **同号自检**：闸门比对目录名轮次、文件名后缀、`manifest.doc_round` 三处，必须完全一致。
6. **manifest 必登记**：`doc_round`、`template_version`（逐文档）、`template_sha`（逐份基线件）、`software_version`、
   每份页数、脚本版本、事实与说明书哈希（如 `facts_sha` / `ifu_sha`）、产物与配图哈希、各检查报告哈希、
   `supersedes`（本版取代哪一版）、`entity_mode`（生产主体形态）、变更摘要。
   检查报告本体落工作目录，manifest 只记路径与哈希，不必塞进交付目录。

判据口径见 `pitfalls.md` §83（换项目要重设的项目级口径）与 §88（版本命名与默认轮次）。

## 10. 每次修复或变更都递增版本并保留修改记录（2026-11-24 用户确认）

1. **触发范围无小改例外**：每次针对项目产物修复问题、纠正错误、调整格式、修改内容或落实需求变更，都生成下一个版本。只改一个字、只修一份、只恢复页眉也不能覆盖原版；不以“补丁”“重导出”“同版重建”绕过递增。
2. **版本号连续现场推导**：读取项目已存在的最大有效轮次，使用其下一轮；目录、文件后缀和manifest轮次一致。不能按“格式=V2、内容=V3”固定分配版本；不能写死默认轮次。每次操作打印来源版本、本轮版本及变更原因。
3. **旧版本完整保留**：既有目录、文件、清单、修改记录和对应验证证据按历史只读保留。禁止覆盖、删除或把旧目录改名后复用原轮次；--force不构成本规则的豁免。回退也应产生新的下一版本，并说明回退到哪一历史内容。
4. **每个版本都有独立修改记录**：在该版本目录保存`修改记录_V{n}.md`。项目已由`生成记录_V{n}.md`承载完整修改信息时可沿用既定命名，避免两份竞争台账；但必须明确包含下列内容，不能只有“已优化/已修复”或口头说明、Git提交。

   | 字段 | 必须记录 |
   |---|---|
   | 本版与来源 | 当前版本、来源/取代版本、日期、工作稿或受控状态 |
   | 触发原因 | 用户需求变更、错误现象或问题编号，为什么修改 |
   | 修改位置 | 涉及文件、章节、表格、页眉/页脚或数据字段 |
   | 改前与改后 | 可核对的差异及处理方式；规则/门禁的调整也单独列出 |
   | 保持项 | 明确要求保留的模板结构、模板版号及未改变的产品事实 |
   | 验证 | 实际执行的命令/方法、结果、页数与有关证据；未执行项写原因 |
   | 未决项 | 剩余问题、风险、需要补充的证据，不把未测写成通过 |
   | 关联清单 | 本版产物、修改记录与验证报告的路径及哈希由manifest关联 |

5. **形成可追溯版本链**：项目可维护按版本追加的修改总览，指向各版独立修改记录；manifest登记`doc_round`、`supersedes`、变更摘要和修改记录路径/哈希。历史记录有误时追加更正与依据，不悄悄改写旧记录。
6. **交付门禁**：下一版本未递增、目标版本已存在、缺少对应修改记录、记录无法对应实际文件或清单哈希不同代，均不得声称本轮已完成。仅检查、未改项目产物时留检查报告，不为了记录流程规则而自动重生成无关产品文档。
7. **三种版本不得混淆**：上述递增指文档交付轮次，不自动改变页眉中的模板版号或正文的软件发布版本。相关格式仍只遵循格式主文件，不能为“升版本”删除、重建或改写模板页眉。

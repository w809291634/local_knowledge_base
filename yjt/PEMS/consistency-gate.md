# 一致性闸门：多文档同数据对账（通用）

> 适用：文档族内部必须互相一致（型号、编号、版本、指标、术语）的任何场景；
> 医疗器械注册资料尤其严格——**同一数据不一致是发补首因**。

## 结论先行

一致性检查分三层：

1. **集合层**（可自动化）：同一清单在各文档中的集合是否相等（型号集合、附件集合、用例集合）。
2. **字段层**（半自动）：同一主键（如型号）在各文档中的字段取值是否一致（可勾选/可选/数量）。
3. **关键字层**（可自动化）：关键项是否**覆盖**于各文档（安全阈值、时间范围、标准号、编号前缀）。

**正确性与完整性必须人工**：图内容、签署栏、交叉引用文件名、图文是否吻合。

## 1. 建立「对照表」

把每类数据指定「权威出处」，其余文档必须跟随：

| 数据项 | 权威出处（示例） | 需同步的文档 |
|---|---|---|
| 型号清单与每型号配置 | 产品技术要求 / 型号规格表 | 说明书、需求、设计、描述、验证、确认 |
| 文件编号规则 | 体系文件规定 | 所有文档封面/页眉/正文引用 |
| 版本号与命名规则 | 命名规则文件 | 软件类全部文档 |
| 性能指标 | 产品技术要求 | 说明书、需求、验证/确认用例 |
| 术语（部件名称） | 说明书 | 其余全部 |

## 2. 自动化检查要点

```bash
python tools/consistency_check.py --config config.json
```

- **主键正则**（如型号 `[A-Z]{2,3}-\d{5}`）配在 config 里，跨项目可换。
- 集合差集：报告「A 有 B 无」。**A 有而 B 无 = 覆盖范围不一致**（最严重）。
- 同键取值比对：把各文档中同一型号所在行的字段抽出来对比，报「取值相反」。
- 关键字覆盖：安全项（阈值、保护动作）在需求/设计/验证三处都要出现。

## 3. 典型冲突模式（换项目同样会遇到）

| 模式 | 表现 | 根因 |
|---|---|---|
| 覆盖范围不一致 | 文档甲 30 条、文档乙 40 条 | 各自抄了不同来源 |
| 同键取值相反 | 同一型号「可选」在甲为 √、乙为 / | 排序规则不同（奇偶/分组） |
| 术语漂移 | 甲「照射器」乙「探头」 | 未统一术语表 |
| 版本写法不一 | `V1` vs `V1.0` vs `V1.0.0.0` | 未区分「发布版本/完整版本」 |
| 指标自相矛盾 | 「不超过 X ±20%」 | 表述本身逻辑冲突 |
| 章节号/错别字 | `1,3,2`、`4..1.3`、形近错字 | 模板复用未校对 |
| 追溯断链 | 引用文档名实际不存在 | 引用未随改名更新 |

## 4. 人工必查四项

1. **图**：体系结构图/框图/流程图/界面图——脚本读不到图内文字；沿用他项目模板时图上
   文字很可能还是旧的。
2. **签署栏**：编制/审核/批准、测试人/测试时间是否填写。
3. **交叉引用**：文中引用的文档名是否真实存在且一致。
4. **他项目残留**：别家公司代号、他项目产品名、外来内部文件名、模板批注。

## 5. 处置原则

- 先**定基线**（哪份为准），再全文统一——不要在未定基线时逐份小修。
- 冲突清单按「影响范围」排序：影响多份文档的先解决。
- 每次修改后**重跑对账**，直到三份完全一致。

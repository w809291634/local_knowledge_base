# 一致性闸门：多文档同数据对账（通用）

> 适用：文档族内部必须互相一致（型号、编号、版本、指标、术语）的任何场景；
> 医疗器械注册资料尤其严格——**同一数据不一致是发补首因**。

## 结论先行

一致性检查分三层：

1. **集合层**（可自动化）：同一清单在各文档中的集合是否相等（型号集合、附件集合、用例集合）。
2. **字段层**（半自动）：同一主键（如型号）在各文档中的字段取值是否一致（可勾选/可选/数量）。
3. **关键字层**（可自动化）：关键项是否**覆盖**于各文档（安全阈值、时间范围、标准号、编号前缀）。

**正确性与完整性必须人工**：图内容、签署栏、交叉引用文件名、图文是否吻合。

**外加一层（每轮交付的最后一步，必做）**：**三方收口** —— 说明书 / 代码 / 注意事项 逐参数核对（第 5 节）。
文档族内部一致 ≠ 与真机一致；说明书写的数字必须能在代码里找到出处。

## 1. 建立「对照表」

把每类数据指定「权威出处」，其余文档必须跟随：

| 数据项 | 权威出处（示例） | 需同步的文档 |
|---|---|---|
| 型号清单与每型号配置 | 产品技术要求 / 型号规格表 | 说明书、需求、设计、描述、验证、确认 |
| 文件编号规则 | 体系文件规定 | 所有文档封面/页眉/正文引用 |
| 版本号与命名规则 | 命名规则文件 | 软件类全部文档 |
| 性能指标 | 产品技术要求 | 说明书、需求、验证/确认用例 |
| 术语（部件名称） | 说明书 | 其余全部 |

## 2. 自动化检查要点

```bash
python tools/consistency_check.py --config <project-config.json>
```

- **主键正则**（如型号 `[A-Z]{2,3}-\d{5}`）配在 config 里，跨项目可换。
- 集合差集：报告「A 有 B 无」。**A 有而 B 无 = 覆盖范围不一致**（最严重）。
- 同键取值比对：把各文档中同一型号所在行的字段抽出来对比，报「取值相反」。
- 关键字覆盖：安全项（阈值、保护动作）在需求/设计/验证三处都要出现。

## 3. 典型冲突模式（换项目同样会遇到）

| 模式 | 表现 | 根因 |
|---|---|---|
| 覆盖范围不一致 | 文档甲 30 条、文档乙 40 条 | 各自抄了不同来源 |
| 同键取值相反 | 同一型号「可选」在甲为 √、乙为 / | 排序规则不同（奇偶/分组） |
| 术语漂移 | 甲「照射器」乙「探头」 | 未统一术语表 |
| 版本写法不一 | `V1` vs `V1.0` vs `V1.0.0.0` | 未区分「发布版本/完整版本」 |
| 指标自相矛盾 | 「不超过 X ±20%」 | 表述本身逻辑冲突 |
| 章节号/错别字 | `1,3,2`、`4..1.3`、形近错字 | 模板复用未校对 |
| 追溯断链 | 引用文档名实际不存在 | 引用未随改名更新 |

## 4. 人工必查四项

1. **图**：体系结构图/框图/流程图/界面图——脚本读不到图内文字；沿用他项目模板时图上
   文字很可能还是旧的。
2. **签署栏**：编制/审核/批准、测试人/测试时间是否填写。
3. **交叉引用**：文中引用的文档名是否真实存在且一致。
4. **他项目残留**：别家公司代号、他项目产品名、外来内部文件名、模板批注。

## 5. 交付前多源收口（每轮必做）

> 文档族内部一致不等于与产品事实一致。每项声明都应根据性质核对相应的受控来源：说明书、注意事项、技术要求、型号差异表、源码、硬件/BOM、图纸、风险文件、检验记录或临床/可用性证据。

### 5.1 按声明类型选择对照来源

| 声明类型 | 必核来源 | 核对重点 |
|---|---|---|
| 型号、配置、适用范围 | 说明书、技术要求、型号差异表 | 型号范围、选配功能、附件和适用条件一致 |
| 交互、状态机、通信、时间、提示和保护逻辑 | 源码、接口定义、说明书、注意事项 | 行为、边界、异常处理和用户反馈一致 |
| 波长、功率、电气、尺寸、供电和硬件接口 | 技术要求、BOM、图纸、检验记录 | 物理参数不能仅用代码或说明书推定 |
| 风险控制和剩余风险 | 风险文件、设计、验证证据、说明书 | 控制措施、验证方式和用户信息一致 |
| 版本、哈希和发布状态 | 版本库、构建记录、发布清单 | 发布版本、完整版本和文档版本可追溯 |

### 5.2 必核声明清单

- 用户可设置或观察到的时间、档位、模式、阈值、提示、交互和自动处理；
- 型号/配置差异、可选通信或附件范围；
- 安全相关的停止、互锁、异常、恢复和用户警示；
- 物理性能、环境条件、硬件接口和适用范围；
- 软件版本、文档版本、构建版本和提交版本。

每项声明应标注其权威来源类型。若同一事实在不同来源的数值、单位、测量位置、适用型号或状态不同，必须记录差异、确定基线并同步受影响资料。

### 5.3 输出多源核对表

| 参数/条款 | 文档声明 | 权威来源及位置 | 代码/硬件/证据值 | 是否一致 | 处置 |
|---|---|---|---|---|---|
| 示例条款 |  |  |  |  |  |

- 一致：保留核对记录；
- 不一致：确定权威来源后更新全部受影响资料；
- 缺失：补充受控资料或在项目待办中闭环；
- 冲突未清零：不得发布。

## 6. 处置原则

- 先确定事实基线，再全文统一；不要在未定基线时逐份小修。
- 按影响范围和风险优先级处理冲突。
- 修改后重跑一致性检查、全页渲染和多源核对，直至所有受影响条款闭环。

## 7. 段落级一致性（跨文档之外，同一文档内部也要对）

跨文档对账抓不到"同一份文档里同一句话写两遍"和"段落格式不一致"，这两类是发补高频项，
必须单独设层：

| 检查 | 判据 | 不查的后果 |
|---|---|---|
| 文档内重复段 | `dup_kind` 四形态（exact / near / same-lead / contained） | 承接与槽位各写一遍同一内容，读者一眼看到两遍 |
| 段落版式漂移 | 生效版式（docDefaults→样式链→直接 pPr）与就近锚点比对 | 新写正文贴页边，上下文缩进两字符 |
| 承接段顺序 | 产物里承接段的先后与来源版里一致（映射后非递减） | 同锚点多段插入被反序，整章倒着读 |
| 正文预填结论 | 正文段与表格单元格都扫"通过／符合要求"类断言 | 只查结果列会漏：上一版结论被承接到正文段落里 |

三条边界：① 两段都是模板原样时**只报不删**（模板自带的并列条目开头常相同）；
② 删重复段前先确认保留段已覆盖被删段的**独有事实**，否则去重＝丢信息；
③ 版式判定依赖"每段来历"记录，来历缺失就不要动模板段的版式。
